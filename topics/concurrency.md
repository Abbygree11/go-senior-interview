# Конкурентность

В этом разделе будут сохраняться разобранные вопросы и правильные ответы.

## Вопрос: Что произойдёт при конкурентном чтении и записи в обычную map? Как выбрать между Mutex, RWMutex и sync.Map?

**Ответ:** Обычная Go `map[K]V` не поддерживает конкурентные чтение и запись (или одновременные записи) без внешней синхронизации. Это **data race**, то есть программа некорректна независимо от того, удалось ли воспроизвести аварию. Рантайм может завершить программу с `fatal error: concurrent map read and map write` или `concurrent map writes`. Это фатальная ошибка рантайма, а не обычная `panic`, которую следует пытаться перехватить через `recover`. Для диагностики гонок полезно запускать тесты и приложения с `-race`. Одновременное чтение `map` из нескольких горутин без записи безопасно.

**Варианты защиты:**

- `map` + `sync.Mutex`: все обращения к общему состоянию защищены `Lock/Unlock`. Простой, понятный вариант для начала.
- `map` + `sync.RWMutex`: чтение защищено `RLock/RUnlock`, изменение — `Lock/Unlock`. Позволяет нескольким читателям работать одновременно, но не гарантирует преимущество в производительности: стоимость блокировок и интенсивность конкуренции нужно измерять.
- `sync.Map`: специализированная конкурентная карта без дополнительной синхронизации для **её отдельных операций**. Документация Go отмечает два удачных сценария: (1) ключ обычно записывается один раз, а затем многократно читается (например, растущий кэш); (2) горутины обращаются к преимущественно непересекающимся наборам ключей. При интенсивных обновлениях одних и тех же ключей `sync.Map` не обязательно быстрее `map` + `RWMutex`.

**Что важно для Senior:** Для кэша «много чтений, мало перезаписей» `sync.Map` — обоснованный кандидат, но это не автоматический победитель. Нужно учесть частоту добавления *новых* ключей, удаления/TTL, количество конкурентных горутин, распределение запросов по ключам, необходимость типобезопасности и согласованных операций над несколькими элементами. У `sync.Map` ключи и значения имеют тип `any`; для типизированных структур и комплексных инвариантов обычная `map` с мьютексом зачастую проще. Если надо атомарно выполнить несколько операций над `sync.Map` как единое целое, её индивидуальная потокобезопасность сама по себе этого не обеспечивает. `Range` не является согласованным снимком всей карты при конкурентных изменениях.

**Пример (`RWMutex`):**

```go
type Cache struct {
    mu sync.RWMutex
    data map[string]string
}

func (c *Cache) Get(key string) (string, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.data[key]
    return v, ok
}

func (c *Cache) Set(key, value string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[key] = value
}
```

Поле `data` должно быть инициализировано до вызова `Set` (например, при создании `Cache` через `make(map[string]string)`).

**Вывод для собеседования:** Выбор надо обосновать паттерном доступа, требованиями к корректности и профилированием/бенчмарками на типичной нагрузке.

Источник: [официальная документация Go, sync.Map](https://pkg.go.dev/sync#Map).


## Вопрос: Чем `nil`-канал отличается от закрытого канала? Как это влияет на `select`?

**Ответ:**

| Операция | `nil`-канал | Закрытый канал |
| --- | --- | --- |
| Чтение (`<-ch`) | Блокируется навсегда | Сначала возвращает элементы буфера, затем сразу возвращает нулевое значение |
| Чтение `v, ok := <-ch` | Блокируется навсегда | После опустошения буфера возвращает `zero, false` |
| Запись (`ch <- v`) | Блокируется навсегда | Вызывает `panic` |
| `close(ch)` | Вызывает `panic` | Повторное закрытие вызывает `panic` |

Операции с `nil`-каналом в `select` никогда не готовы, поэтому соответствующие ветки фактически отключены. Закрытый канал, напротив, после опустошения буфера всегда готов к чтению. Если оставить такую ветку в цикле `select` и при `!ok` просто выполнять `continue`, ветка будет продолжать участвовать в выборе, что может привести к активному циклу и бессмысленной нагрузке на CPU. Если одновременно готовы несколько веток, `select` выбирает одну посредством равномерного псевдослучайного выбора; гарантии приоритета или немедленного выполнения конкретной ветки нет.

**Приём:** когда входной канал закрыт, присвоить `nil` *локальной переменной канала*, отключив ветку `select`; сам исходный канал от этого не меняется.

```go
func process(ch <-chan int, done <-chan struct{}) {
    for {
        select {
        case v, ok := <-ch:
            if !ok {
                ch = nil
                continue
            }
            fmt.Println(v)
        case <-done:
            return
        }
    }
}
```

**Нюансы:** если после `ch = nil` другие ветки могут никогда не стать готовыми (например, `done` тоже `nil`), горутина заблокируется; если все ветки `select` отключены и нет `default`, ожидание бессрочное. Для завершения после закрытия единственного рабочего канала можно просто `return`, а не присваивать `nil`.
