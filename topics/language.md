# Go: язык

В этом разделе будут сохраняться разобранные вопросы и правильные ответы.

## Вопрос: Как устроены слайсы в Go, что передаётся в функцию и когда изменения видны снаружи?

**Ответ:** Слайс `[]T` — представление последовательности элементов в базовом массиве. Его заголовок концептуально содержит указатель на элементы, длину `len` и ёмкость `cap` (ёмкость считается от начала этого слайса до конца доступной ему области базового массива). При передаче слайса в функцию по значению копируется **заголовок**, но не элементы базового массива. Поэтому два заголовка могут ссылаться на один массив.

- Запись `s[i] = x` изменяет элемент общего массива: изменение видно в исходном слайсе, если он охватывает этот элемент.
- `s = s[:1]` меняет только длину **локального заголовка**: `len` исходного слайса не меняется, базовый массив не копируется. У обычного среза `s[:1]` ёмкость остаётся прежней.
- `s = append(s, x)` возвращает слайс с новой длиной. Если текущей ёмкости достаточно, `append` использует тот же массив и может записать элементы, наблюдаемые через другие слайсы. При недостаточной ёмкости выделяется новый базовый массив, и дальнейшие изменения через новый слайс не затрагивают старый массив. В любом случае заголовок исходного слайса в вызывающей функции не обновляется автоматически.
- Если нужно изменить сам слайс у вызывающего кода, обычно возвращают новое значение (`s = modify(s)`); также возможен аргумент `*[]T`.
- В отличие от слайса, массив `[N]T` при передаче по значению копируется целиком (его элементы).

**Пример:**

```go
func modify(s []int) {
    s[0] = 10
    s = append(s, 99)
    s[1] = 20
}

func main() {
    a := make([]int, 2, 3)
    a[0], a[1] = 1, 2

    modify(a)

    fmt.Println(a, len(a), cap(a))
    fmt.Println(a[:3])
}
```

Вывод:

```text
[10 20] 2 3
[10 20 99]
```

`modify` получает копию заголовка `a`. Ёмкости 3 хватает для `append`, поэтому `99` записывается в третий элемент того же массива; длина исходного `a` остаётся 2. `a[:3]` показывает третий элемент.

**Нюанс для собеседования:** Уменьшение длины срезом **не означает** уменьшения его ёмкости. Например:

```go
a := []int{1, 2, 3}
s := a[:1]        // len=1, cap=3
s = append(s, 9)  // перезаписывает a[1]
fmt.Println(a)    // [1 9 3]
```

Если нужно ограничить ёмкость среза, используют полное выражение среза: `s := a[:1:1]` (здесь `len=1, cap=1`). Тогда добавление элемента через `append` требует нового массива.


## Вопрос: Почему интерфейс `error` может быть не равен `nil`, если внутри `nil`-указатель? Поможет ли `error(err)`?

**Ответ:** Интерфейс концептуально хранит динамический тип и динамическое значение. Он равен `nil`, только когда нет ни динамического типа, ни динамического значения. Если указатель типа `*MyError` равен `nil`, но помещён в `error`, интерфейс содержит динамический тип `*MyError` и нулевое значение указателя. Поэтому сравнение `err == nil` даст `false`.

```go
type MyError struct{}

func (*MyError) Error() string { return "my error" }

func doSomething() error {
    var err *MyError = nil
    return error(err) // явное преобразование не исправляет typed nil
}

func main() {
    fmt.Println(doSomething() == nil) // false
}
```

Неявное присваивание при `return err` и явное преобразование `return error(err)` дают тот же результат: динамический тип остаётся `*MyError`. Чтобы сообщить об отсутствии ошибки, нужно **вернуть непосредственно `nil`** из функции с возвращаемым типом `error`. При наличии ошибки вернуть ненулевой экземпляр кастомного типа:

```go
func doSomething(failed bool) error {
    if !failed {
        return nil
    }
    return &MyError{}
}
```

**Практический риск:** проверка `if err != nil` может зайти в ветку обработки ошибки, хотя внутри интерфейса лежит `nil`-указатель. Не нужно путать `nil` интерфейса и типизированный `nil` внутри интерфейса. Представление «тип + значение» — концептуальная модель; внутренние структуры рантайма могут отличаться.

## Вопрос: Как работает `defer` в Go, когда вычисляются аргументы и почему `defer` внутри цикла опасен?

**Ответ:** `defer` откладывает вызов до завершения **окружающей функции** (в том числе при раскрутке стека из-за `panic`). Отложенные вызовы выполняются в порядке LIFO: последний зарегистрированный — первый выполненный. Аргументы отложенного вызова, включая получатель метода, вычисляются во время выполнения оператора `defer`, а не в момент вызова. Тело отложенной функции исполняется позже. При `os.Exit` отложенные вызовы не выполняются.

```go
func example() (result int) {
    x := 10
    defer func() { result += x }()
    defer fmt.Println(x)
    x = 20
    return 5
}

func main() { fmt.Println(example()) }
```

Вывод:
```text
10
25
```

Первый `defer` регистрирует замыкание, которое при выполнении читает `x`. Второй `defer` сразу вычисляет аргумент `x` как 10. После `x = 20` оператор `return 5` устанавливает именованный результат `result = 5`; затем `fmt.Println(x)` печатает сохранённое 10, замыкание добавляет текущее значение `x` (20) к `result`; итог — 25. Замыкания не всегда захватывают «последнее значение»: при передаче переменной параметром отложенного вызова аргумент вычисляется сразу.

**`defer` в цикле:** `defer file.Close()` после `os.Open` на каждой итерации откладывает все закрытия до выхода из окружающей функции, а не до окончания итерации. При большом количестве файлов можно исчерпать лимит открытых дескрипторов. Обычные фигурные скобки `{}` создают область видимости, но не отдельный вызов функции — не меняют момент выполнения `defer`. Решение: вынести обработку файла в отдельную функцию (или немедленно вызываемую анонимную функцию), и тогда её `defer` выполнится при завершении каждой такой функции:

```go
func processFile(path string) error {
    f, err := os.Open(path)
    if err != nil { return err }
    defer f.Close()
    // обработка
    return nil
}

func processFiles(paths []string) error {
    for _, path := range paths {
        if err := processFile(path); err != nil { return err }
    }
    return nil
}
```

Явный `Close()` в цикле тоже может освобождать ресурс вовремя, но важно закрывать его при всех ветках выхода и учитывать возможные ошибки закрытия (особенно при записи). В примере выше ошибка `Close` игнорируется ради краткости.
