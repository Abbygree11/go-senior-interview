# `sync.RWMutex`: читатели, писатели, starvation, обновление состояния

## 1. Устройство

`RWMutex` разрешает конкурентные `RLock` (несколько читателей) **или** эксклюзивный `Lock` (один писатель). Он полезен, если читатели действительно выполняют заметную работу внутри критической секции и конкурируют друг с другом, но не универсально быстрее `Mutex`.

```go
type Cache struct {
    mu sync.RWMutex
    m  map[string]int
}
func (c *Cache) Get(k string) (int, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.m[k]
    return v, ok
}
func (c *Cache) Put(k string, v int) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.m[k] = v
}
```

## 2. Если читатель держит `RLock`, писатель ждёт

Писатель с `Lock` не может войти, пока активные читатели не отпустили свои `RLock`. Когда писатель уже ожидает, **новые читатели блокируются**, чтобы писателя не вытеснил бесконечный поток RLock.

Это не означает идеальной справедливости FIFO, но гарантирует важное свойство протокола: входящие читатели не должны бесконечно оттеснять ожидающего writer.

## 3. Рекурсивный `RLock` может зависнуть

```go
mu.RLock()
// другая горутина теперь ждёт mu.Lock()
mu.RLock() // может блокироваться из-за ожидающего writer
// до mu.RUnlock() не дойдём
```

Поэтому документация прямо запрещает рассчитывать на рекурсивный reader locking. Не думай, что раз читателей разрешено много, то одна горутина всегда может брать `RLock` сколько угодно раз.

## 4. Upgrade/downgrade нет

```go
mu.RLock()
// хотим поменять состояние
mu.Lock() // deadlock: собственный RLock ещё удерживается
```

Нельзя атомарно «повысить» reader lock до writer lock, и обратного безопасного «понижения» тоже нет. Отпусти `RLock`, возьми `Lock`, **повторно проверь условие**, потому что состояние могло измениться между ними.

```go
mu.RLock()
need := value == nil
mu.RUnlock()
if need {
    mu.Lock()
    if value == nil {
        value = build()
    }
    mu.Unlock()
}
```

При этом `build()` может быть дорогим, и его выполнение под write-lock может тормозить читателей. Для одноразовой инициализации иногда лучше `sync.Once`.

## 5. Почему `RWMutex` бывает медленнее `Mutex`

В `RWMutex` дополнительные атомарные операции и координация читателей/писателей. Если критическая секция — одно чтение `map`, а конкуренция невысока, накладные расходы могут превысить выигрыш от параллельности. При частых писателях читатели всё равно регулярно ждут.

**Проверка**: бенчмарки с реальным отношением read/write, числом горутин, размером критической секции, целевым `GOMAXPROCS`.

## 6. Копирование и владение

`RWMutex` имеет zero value, готовый к использованию. Его нельзя копировать после начала использования. `RUnlock` без соответствующего удержания `RLock` — фатальная ошибка. `Lock` и `RLock` не привязаны к горутине-владельцу, но баланс должен быть точным.

## 7. Чтение внешних полей вне `RLock`

```go
c.mu.RLock()
p := c.pointer
c.mu.RUnlock()
use(p)
```

Защищённо лишь чтение самого `pointer`. Если `use(p)` читает **мутабельное содержимое**, которое писатели меняют под тем же mutex, после освобождения `RLock` возникнет data race. Сделай copy-on-read/immutable value или удерживай lock на всю требуемую операцию.

## Дополнительные сложные случаи

### 9. Смена read-lock на write-lock без интервала невозможна

```go
mu.RLock()
if needWrite {
    mu.RUnlock()
    mu.Lock()
    if needWriteNow() {
        mutate()
    }
    mu.Unlock()
} else {
    mu.RUnlock()
}
```

Между `RUnlock` и `Lock` другая горутина может изменить `needWriteNow`. **Почему:** `RWMutex` не предоставляет upgrade с атомарным переводом одной блокировки в другую. Поэтому обязательно повторить проверку.

### 10. Рекурсивный `RLock` может привести к взаимной блокировке из-за writer

Горутина A держит `RLock`. Горутина B приходит за `Lock` и ждёт A. Затем A хочет взять второй `RLock`: новый reader блокируется из-за ожидающего writer. A не может отпустить первый `RLock`, потому что застряла на втором. Это deadlock, несмотря на тезис «несколько читателей могут читать одновременно».

### 11. Возврат map/указателя под `RLock` не защищает дальнейшее использование

```go
func (c *Cache) Snapshot() map[string]int {
    c.mu.RLock()
    defer c.mu.RUnlock()
    return c.m // возвращён тот же объект map
}
```

Вызвавший код может читать map **после освобождения lock**, пока писатели меняют её → race. Чтобы вернуть снимок, `maps.Clone(c.m)` под `RLock`. Вложенные mutable значения всё равно требуют отдельного копирования.

### 12. Измерение `RWMutex`

На read-mostly нагрузках с длительными критическими секциями параллельные readers часто выигрывают. На сверхкоротких `map` reads накладные расходы, cache-line contention и блокировки writers могут сделать простой `Mutex` быстрее. Нужно сравнивать **latency percentiles и throughput**, а не только `ns/op` одного микробенчмарка.

Источники: [sync.RWMutex](https://pkg.go.dev/sync#RWMutex), [Go Memory Model](https://go.dev/ref/mem).
