# `sync.Cond`: ожидание условия и потерянные уведомления

## 1. Модель

`sync.Cond` — механизм ожидания **изменения разделяемого состояния**, защищённого связанным `Locker` (обычно `*sync.Mutex`). `Wait` атомарно отпускает lock, переходит в ожидание, а после сигнала снова захватывает lock перед возвратом.

Важно: `Cond` не хранит «счётчик сигналов» как очередь сообщений. **Истина живёт в условии, а не в `Signal`**.

## 2. Канонический код

```go
mu := &sync.Mutex{}
cond := sync.NewCond(mu)
ready := false

go func() {
    mu.Lock()
    for !ready { // проверяем внутри цикла, под lock
        cond.Wait()
    }
    // безопасно использовать состояние, защищённое mu
    mu.Unlock()
}()

mu.Lock()
ready = true
cond.Broadcast()
mu.Unlock()
```

Цикл необходим, потому что состояние может измениться между уведомлением и повторным получением lock; несколько проснувшихся workers могут конкурировать за один ресурс.

## 3. Потерянный сигнал

`Signal()`, вызванный **до** начала ожидания, не оставляет «жетон» на будущее. Поэтому код, где worker без проверки состояния просто вызывает `Wait()`, может зависнуть, даже если «сигнал уже был».

Правильно: проверять predicate под тем же lock, под которым он изменяется.

## 4. `Signal` vs `Broadcast`

`Signal` пробуждает одного ожидающего, `Broadcast` — всех. Но это не гарантирует, что всякая пробуждённая горутина сразу увидит истинное условие: перед возвратом нужно получить lock, и состояние может поменяться. При `Broadcast` появляется эффект «стада» (много проснувшихся горутин конкурируют за lock).

## 5. Контекст и `Cond`

`Wait` не принимает `context.Context`. Для отмены нужно проектировать отдельный протокол изменения predicate + уведомления или выбрать каналы/другой примитив. Нельзя просто вызвать `cancel()` и ожидать, что `Wait` автоматически завершится.

## 6. Копирование и ошибки

`sync.Cond` нельзя копировать после первого использования. `Wait` требует, чтобы вызывающий уже держал связанный lock; иначе поведение неверно (обычно runtime fatal error при разблокировке незахваченного mutex).

## 7. Когда предпочесть канал

Канал удобно передаёт значения или одноразовый broadcast через close. `Cond` удобен, если много workers ждут **произвольного predicate** над общим состоянием и требуется переоценка условия под mutex. Не подменяй `Cond` каналом только потому, что «в Go всё должно быть через каналы».

## 8. Вопросы

Почему `Wait()` должен вызываться в `for`? Куда пропадает `Signal`, отправленный до `Wait`? Почему `Broadcast` не значит, что условие всё ещё истинно у каждого проснувшегося worker? Как корректно реализовать отмену?

## Ещё несколько причин трудных ошибок с Cond

### 9. `Wait()` возвращает после `Signal`, но predicate уже может быть ложным

```go
c.L.Lock()
for available == 0 {
    c.Wait()
}
available--
c.L.Unlock()
```

Если `Broadcast` разбудил десять workers, а доступный элемент один, первый может его забрать. Остальные должны **перепроверить условие**, а не считать `Signal` разрешением продолжать.

### 10. `Signal` не эквивалентен `send`

`Cond` — уведомление о возможном **изменении состояния**, а не очередь событий с накоплением. Если отправить `Signal` раньше, чем кто-то начал `Wait`, будущий `Wait` не «воспроизведёт» уведомление. Поэтому predicate должен храниться отдельно под lock.

### 11. Сигнал можно посылать без удержания `L`, но важна координация состояния

Документация допускает `Signal/Broadcast` без удержания `c.L`. Однако изменение самого predicate обычно защищено связанным `L`; новичок легко создаёт race, если меняет поле без lock и полагается на `Signal` как на magic synchronization. Уведомление не заменяет защиту данных.

### 12. `Wait` не имеет встроенной отмены

`cancel()` не снимает блокировку `c.Wait()`, если никто не уведомил условную переменную. Для остановки можно изменить `stopping` под lock и сделать `Broadcast`, а waiter проверяет `stopping` в том же цикле:

```go
c.L.Lock()
for !ready && !stopping { c.Wait() }
c.L.Unlock()
```
