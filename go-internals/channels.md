# Каналы (`chan T`): внутренности, операции, закрытие, блокировки, гонки протокола

## 1. Модель runtime и типы

Канал создаётся `make(chan T, capacity)`. Концептуально runtime хранит внутреннюю структуру (в реализации Go используется `hchan`) с синхронизацией, очередью ожидающих отправителей, очередью ожидающих получателей, счётчиком элементов, размером буфера и признаком закрытия. Поля/алгоритмы могут меняться — **публичный контракт определяется спецификацией**.

Направления: `chan T` — двусторонний, `chan<- T` — только отправка, `<-chan T` — только получение. Канал — сравнимое значение; копии переменной `ch2 := ch1` ссылаются на один канал. При передаче в функцию по значению не создаётся новая очередь.

Не путать `nil`-канал, открытый канал с пустым буфером и **закрытый** канал — это разные состояния.

## 2. Unbuffered: rendezvous отправителя и получателя

`make(chan int)` эквивалентен `make(chan int, 0)`. У небyферизованного канала отправка завершается, когда соответствующий приём может принять значение. Элемент не «лежит в очереди» до появления получателя.

```go
ch := make(chan int)
go func() { ch <- 42 }()
fmt.Println(<-ch) // 42
```

**Каверза:** отправить `ch <- 42` и только потом получить `<-ch` в **той же** горутине без второй стороны — блокировка. Runtime может диагностировать глобальный deadlock, если ни одна горутина не может продвинуться, но наличие других активных горутин может скрывать локальный deadlock.

**Память:** отправка на канал синхронизируется с завершением соответствующего приёма. Это часть happens-before, не просто передача байтов.

## 3. Buffered: очередь с ограниченной ёмкостью

```go
ch := make(chan int, 2)
ch <- 1
ch <- 2
// ch <- 3 // блокируется, пока не освободится место
fmt.Println(<-ch, <-ch) // 1 2
```

Буфер сохраняет FIFO-порядок значений **для одного канала**. Он не обещает порядок выполнения горутин, отправляющих конкурентно. `len(ch)` — число буферизованных значений на момент наблюдения, а не резерв ёмкости: между проверкой `len` и `send` другой отправитель может заполнить буфер.

Буфер не решает проблему обратного давления: когда потребитель отстаёт, отправители всё равно блокируются.

## 4. Матрица состояний

| Операция | `nil` | Открытый, операция не готова | Закрытый |
|---|---|---|---|
| `<-ch` | ждёт бесконечно | ждёт отправки/буфера | отдаёт буфер, затем zero value |
| `v, ok := <-ch` | ждёт бесконечно | ждёт | после буфера: `zero, false` |
| `ch <- x` | ждёт бесконечно | ждёт места/приёма | **panic** |
| `close(ch)` | **panic** | закрывает | повторное закрытие — **panic** |

«Бесконечно» значит без другого механизма отмены/разблокировки; сам `nil` никогда не станет готовым, пока переменная в *новом* выражении не начнёт ссылаться на другой канал.

## 5. Закрытый канал: данные ещё остаются

```go
ch := make(chan int, 2)
ch <- 5
ch <- 6
close(ch)
fmt.Println(<-ch) // 5
fmt.Println(<-ch) // 6
v, ok := <-ch
fmt.Println(v, ok) // 0 false
```

Закрытие означает «новых сообщений больше не будет», а не «буфер очищается». Итерация `for v := range ch` завершится только после закрытия **и исчерпания** буфера. Для читателя закрытие — сигнал конца потока.

## 6. Кто имеет право закрывать?

Обычно единственный владелец отправки закрывает канал; при нескольких отправителях его закрывает **координатор после подтверждения завершения всех отправителей**. Проверка «канал ещё открыт?» перед записью не защищает: между проверкой и операцией состояние может поменяться.

```go
results := make(chan int)
var wg sync.WaitGroup
for i := 0; i < 4; i++ {
    wg.Add(1)
    go func(id int) {
        defer wg.Done()
        results <- id
    }(i)
}
go func() {
    wg.Wait()
    close(results)
}()
for v := range results {
    fmt.Println(v) // порядок НЕ гарантирован
}
```

**Каверза:** если никто не читает из небyферизованного `results`, отправители не завершатся, `wg.Wait()` не вернётся, закрытие не произойдёт. Координатор сам по себе не решает проблему отмены.

## 7. `cancel()` не разблокирует оператор отправки

```go
// Небезопасно при остановленном потребителе:
results <- value
```

Если канал заполнен, горутина останется заблокированной, несмотря на `cancel()`. Используй:

```go
select {
case results <- value:
case <-ctx.Done():
    return
}
```

**Тонкость:** при готовых обеих ветках `select` может всё-таки отправить **после** отмены: это не строгий запрет поздних отправок. Для такого инварианта нужен дополнительный синхронизированный протокол.

**Другая тонкость:** не закрывай `results` сразу после `cancel()`: отправитель ещё может попытаться отправить и получить panic. Сначала дождись завершения всех отправителей.

## 8. Канал как сигнал без полезной нагрузки

`chan struct{}` часто используют для одноразового уведомления. `close(done)` делает чтение готовым **для любого числа** получателей. В отличие от отправки одного значения, закрытие можно использовать для broadcast.

```go
done := make(chan struct{})
go func() {
    <-done
    fmt.Println("stopped")
}()
close(done)
```

Закрывать `done` должен один владелец, либо закрытие защищают `sync.Once`. Повторное закрытие — panic. В большинстве API для отмены предпочтительнее `context.Context`.

## 9. Канал — не универсальный mutex

Буфер `make(chan struct{}, 1)` может служить семафором на один слот; с размером N — ограничителем конкуренции:

```go
sem := make(chan struct{}, 3)
sem <- struct{}{}      // acquire (может блокироваться)
defer func() { <-sem }() // release
```

Плюсы — легко вписать отмену через `select`. Минусы — нужно строго сохранять баланс приобретений и освобождений. Для обычной защиты структуры `sync.Mutex` обычно проще и понятнее.

## 10. Передача значений ≠ глубокое копирование

```go
data := []int{1, 2}
ch := make(chan []int, 1)
ch <- data
received := <-ch
received[0] = 9
fmt.Println(data[0]) // 9
```

Канал передал **значение заголовка слайса**; backing array общий. То же относится к указателям, map, структурам со ссылочными полями. Канал упорядочивает передачу, но не делает произвольное общее состояние потокобезопасным: договорись о передаче владения или копируй.

## 11. Канал и память: когда синхронизация действительно есть

`close(ch)` синхронизируется с получением, которое наблюдает закрытие. У буферизованного канала связь «отправка — соответствующий приём» есть, но утверждение «все действия после любой отправки строго упорядочены с произвольными читателями» неверно. Для сложных схем сверяйся с Go memory model.

## 12. Типовые сценарии утечек

- Производитель ждёт отправки, а потребитель ушёл по ошибке.
- Потребитель ждёт чтения, но ни один отправитель не закроет канал.
- Горутина ждёт `<-ctx.Done()` с `context.Background()` (у него `Done() == nil`).
- `for range` по каналу никогда не завершится, пока живы отправители и канал открыт.
- Канал закрыли слишком рано: `send on closed channel`.

**Защита:** контракт владельца канала, отменяемые блокирующие операции, `WaitGroup`, закрытие после всех отправителей и тесты с `-race` плюс leak-тесты.
