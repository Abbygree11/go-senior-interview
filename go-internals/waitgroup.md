# `sync.WaitGroup`: счётчик, регистрация задач, ловушки `Add/Wait`

## 1. Модель

`WaitGroup` содержит состояние, представляющее количество незавершённых задач; `Add(n)` увеличивает счётчик, `Done()` эквивалентен `Add(-1)`, `Wait()` ждёт обнуления. Внутреннее атомарное состояние и механизмы ожидания — детали runtime, а **контракт API важнее конкретной раскладки битов**.

Нулевое значение готово к использованию. `WaitGroup` нельзя копировать после начала использования.

## 2. Верная последовательность

```go
var wg sync.WaitGroup
for i := 0; i < 5; i++ {
    wg.Add(1) // до запуска
    go func(i int) {
        defer wg.Done()
        work(i)
    }(i)
}
wg.Wait()
```

`wg.Wait()` здесь дожидается всех пяти задач. Порядок работы, результатов и расписание горутин не гарантируются.

## 3. Почему `Add` внутри `go` ошибочен

```go
for i := 0; i < 5; i++ {
    go func() {
        wg.Add(1) // может произойти слишком поздно
        defer wg.Done()
        work()
    }()
}
wg.Wait() // может увидеть ноль ДО первого Add
```

Получается **ранний возврат Wait**: задачи не зарегистрированы до начала ожидания. Для положительных `Add` при нулевом счётчике требуется начать регистрацию до соответствующего `Wait`.

## 4. Двойной `Done` и пропущенный `Done`

Слишком много вызовов `Done` => отрицательный счётчик => **panic**. Слишком мало => `Wait` никогда не завершится (если недостающий Done не произойдёт позднее). `defer wg.Done()` сразу в начале задачи помогает пережить ранний `return` и panic-unwind, но **не спасает от бесконечно заблокированной функции**.

## 5. Повторное использование и `WaitGroup.Go`

Использовать группу для новой партии работ допустимо **после** полного `Wait` прошлой партии. Нельзя начинать новую партию с конкурирующим `Wait` при нулевом счётчике без надлежащей координации.

С Go 1.25 есть `wg.Go(f)`, который регистрирует задачу и запускает её в новой горутине:

```go
var wg sync.WaitGroup
for range 5 {
    wg.Go(func() {
        work()
    })
}
wg.Wait()
```

Контракт `WaitGroup.Go`: функция `f` **не должна паниковать**. Это не замена обработке ошибок.

## 6. WaitGroup != cancellation и != error aggregation

`wg.Wait()` не передаёт ошибку: если воркер вернул `error`, его нужно обработать отдельно. `WaitGroup` не умеет отменять зависший worker. Для группы с общей ошибкой и отменой уместен `golang.org/x/sync/errgroup` с `WithContext` (при корректной проверке контекста в задачах).

## 7. WaitGroup и каналы

```go
results := make(chan int)
var wg sync.WaitGroup
for i := 0; i < 3; i++ {
    wg.Add(1)
    go func(v int) {
        defer wg.Done()
        results <- v
    }(i)
}
go func() {
    wg.Wait()
    close(results)
}()
for v := range results {
    fmt.Println(v)
}
```

**Каверза:** если `wg.Wait()` выполняется до начала чтения `results` в той же горутине, producers зависнут на send и `Wait` не завершится. Закрывать `results` следует после завершения **всех отправителей**, а читать одновременно.

## 8. happens-before

`Done` задачи синхронизируется с возвращением `Wait`, которое она разблокировала. Но `WaitGroup` не делает **произвольные общие записи между workers** безопасными: если два workers пишут в одну map, по-прежнему нужна синхронизация между ними.

## Дополнительные гонки при регистрации задач

### 10. `WaitGroup.Go` не возвращает ошибку

`wg.Go(func(){ work() })` (Go 1.25+) регистрирует и запускает worker, но сигнатура worker — `func()`, без результата. Если нужен первый error с отменой остальных, рассмотрите `errgroup.WithContext`; `WaitGroup.Go` — **примитив завершения**, а не error aggregation.

### 11. `Add(1)` после `go` нарушает регистрацию

Если `wg.Wait()` видит счётчик 0, он может вернуть управление **до** того, как горутина вызвала `Add(1)`. «Но у меня почти всегда работало» не исправляет протокол — порядок исполнения goroutines не определён.

### 12. Копирование группы после использования

```go
var wg sync.WaitGroup
wg.Add(1)
other := wg // НЕЛЬЗЯ полагаться на копию
_ = other
wg.Done()
wg.Wait()
```

`WaitGroup` содержит изменяемое синхронизационное состояние, которое нельзя копировать после первого использования. Так особенно легко ошибиться в value receiver структуры с полем `wg`.

### 13. Зависший worker делает `Wait` бесконечным

Если worker блокируется на `out <- v`, а никто не читает, `Done()` не будет вызван до разблокировки (даже если написан `defer wg.Done()`). `WaitGroup` ничего не отменяет — для завершения нужен `select` с `ctx.Done()` и адекватный lifecycle consumer.

### 14. Новый цикл после завершения

Повторное использование одной группы для следующей партии допустимо только после того, как все предыдущие `Wait` завершились. Если новые вызовы `Add` начинаются конкурентно с `Wait` на **пустой** группе, `Wait` может не учесть новые задачи.
