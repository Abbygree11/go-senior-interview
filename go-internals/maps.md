# `map[K]V`: устройство, nil, ключи, рост, итерация, конкурентность

## 1. Модель и контракт

`map` — хеш-таблица: ключ преобразуется в хеш, по нему находится место хранения; коллизии разрешаются внутренним алгоритмом. **Точное размещение и алгоритм зависят от версии Go**. Начиная с Go 1.24 реализация встроенной map основывается на Swiss Tables; интервью-объяснения исключительно через старые buckets/overflow/эвакуацию не универсальны.

`map` — ссылкоподобное значение. При `m2 := m1` обе переменные работают с одной map. Это не означает, что `map` — указатель в исходном типе, и нельзя присваивать напрямую `*map` вместо `map`.

`K` должен быть сравним. Строки, числа, указатели, массивы из сравнимых элементов допустимы; слайсы, карты, функции — нет. Для интерфейсного ключа динамическое несравнимое значение может вызвать panic при хешировании/сравнении.

## 2. Nil map: чтение разрешено, запись — panic

```go
var m map[string]int
fmt.Println(m == nil, len(m)) // true 0
fmt.Println(m["x"])           // 0
v, ok := m["x"]
fmt.Println(v, ok)            // 0 false
delete(m, "x")                // допустимо
m["x"] = 1                    // panic: assignment to entry in nil map
```

Инициализация: `make(map[string]int)` либо литерал `map[string]int{}`. Ключ может существовать со значением 0, поэтому для проверки присутствия обязателен `comma-ok`.

## 3. Map — совместно используемое состояние

```go
a := map[string]int{"x": 1}
b := a
b["x"] = 2
fmt.Println(a["x"]) // 2
```

Параметр функции `func f(m map[string]int)` тоже получает значение, указывающее на общую внутреннюю таблицу. В отличие от слайса, добавление ключей через это значение видно вызывающему коду. **Однако `m = make(map[...])` внутри функции переназначит лишь локальную переменную.**

## 4. Взятие адреса элемента и изменение структур

```go
type User struct{ Age int }
m := map[string]User{"a": {Age: 10}}
// m["a"].Age++     // ошибка компиляции
u := m["a"]         // локальная копия значения
u.Age++
m["a"] = u          // перезаписать значение целиком
```

Элемент map не адресуем: таблица может перестраиваться/перемещать записи. `&m["a"]` также нельзя. Альтернатива — `map[string]*User`, но тогда появляется разделяемый мутируемый объект и необходимость синхронизации при конкуренции.

## 5. Порядок итерации намеренно не определён

```go
m := map[string]int{"a": 1, "b": 2, "c": 3}
for k, v := range m {
    fmt.Println(k, v) // порядок НЕ определён, не рассчитывать на него
}
```

Даже два прохода могут отличаться. При добавлении ключей во время итерации новые ключи **могут быть посещены или нет**. Удалённые до посещения ключи не выдаются. Это правило касается допустимого обхода в одной горутине; конкурентная модификация без синхронизации — отдельно запрещённый data race.

Для стабильного порядка: собрать ключи, `slices.Sort(keys)`, обходить по списку.

## 6. Конкурентный доступ: гарантии и аварии

Много читателей без писателей — допустимо. Читатель + писатель либо два писателя без синхронизации — **data race**. Runtime иногда завершает процесс с `fatal error: concurrent map read and map write` или `concurrent map writes`; это не просто panic, перехватываемая `recover`. Отсутствие аварии **не доказывает безопасности**.

Варианты: обычная map + `sync.Mutex` / `sync.RWMutex`; специализированная `sync.Map` для подходящего шаблона нагрузки; разбиение по владельцам/шардам.

```go
type Counter struct {
    mu sync.Mutex
    m  map[string]int
}
func (c *Counter) Inc(k string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.m[k]++
}
```

Проверка `if m[k] == 0 { m[k] = 1 }` **не становится атомарной** только потому, что отдельные обращения к конкурентной map потокобезопасны. Для сложных инвариантов защищать нужно всю логическую транзакцию.

## 7. Ключи с `NaN`, интерфейсами, указателями

`math.NaN() != math.NaN()`. Поэтому `float64` допустим как ключ, но поиск по NaN не ведёт себя как обычное сравнение равных чисел. **Не используй NaN как идентификатор, для которого требуется гарантированный повторный поиск.**

Указатели сравниваются по адресам, а не по содержимому объектов. Мутация **самого значения, от которого вычисляется хеш ключа**, после помещения в map может сделать логическое состояние ключа непредсказуемым: делай ключи неизменяемыми.

Интерфейсные ключи: `map[any]int` компилируется, но `m[[]int{1}] = 1` запаникует при выполнении (dynamic type несравним).

## 8. Две map не сравниваются через `==`

`m1 == m2` — ошибка компиляции (кроме сравнения map с `nil`). Для содержимого `maps.Equal` при сравнимых значениях либо предметная логика. Даже при структурном равенстве порядок итерации не становится определённым.

## 9. `clear`, `delete`, память

`delete(m, k)` для отсутствующего ключа безопасен. `clear(m)` удаляет все записи, но не обещает немедленно вернуть всю внутреннюю память ОС. Для сокращения занимаемого места иногда проще построить новую map и перестать ссылаться на старую, **если нет других владельцев старой**.

## Дополнительные реальные ловушки `map`

### 11. `map` со слайсом как значением: append в одну строку корректен

```go
m := map[string][]int{}
m["a"] = append(m["a"], 10)
m["a"] = append(m["a"], 20)
fmt.Println(m["a"]) // [10 20]
```

**Почему:** чтение отсутствующего ключа возвращает nil-слайс, а `append(nil, x)` создаёт backing array. Но при конкурентных `append` одной записи map всё ещё нужна синхронизация.

### 12. `m[k]++` не делает read-modify-write атомарным

```go
m := map[string]int{"count": 0}
m["count"]++
```

В **одной** горутине корректно. В нескольких горутинах — data race; при попытке «заменить на `sync.Map`» пара `Load→Store` всё равно теряет инкременты. Для счётчика по ключу — защищённый lock или отдельный `*atomic.Int64` с продуманной инициализацией.

### 13. Разрушительная ловушка `NaN` как ключа

```go
m := map[float64]string{}
n := math.NaN()
m[n] = "lost"
fmt.Println(n == n) // false
_, ok := m[n]
fmt.Println(ok) // false
```

**Почему:** сравнение NaN с самим собой ложно; lookup не может найти исходный ключ через обычное равенство. Ключ **существует** в таблице (`len(m)==1`), но адресовать его обычным поиском/`delete(m,n)` нельзя. `clear(m)` всё ещё удаляет все записи.

### 14. Итерация, удаление и добавление

Из спецификации следует, что удалённая до посещения запись не будет выдана итератором, а новая запись **может быть выдана или пропущена**. Обход не упорядочен; нельзя делать «псевдодетерминированные» алгоритмы, модифицируя карту на ходу и ожидая фиксированного результата.

### 15. Hash map и детали Swiss Tables

С Go 1.24 реализация использует группы слотов и контрольные байты Swiss Tables, что позволяет искать совпадающие фрагменты хешей пачками и уменьшает промахи памяти. Внутреннее разбиение на таблицы и рост **не часть API**. Для собеседования полезно различать: хеш и сравнимость ключа — семантические требования; контрольные байты и стратегия роста — версия runtime.

### 16. Структура как ключ: осторожно с вложенными полями

```go
type Key struct { Name string; N int }
m := map[Key]string{{"a", 1}: "yes"}
fmt.Println(m[Key{"a", 1}]) // yes
```

Структура сравнима, если сравнимы **все** поля. Нельзя использовать `struct{ Tags []string }` как ключ; даже если в конкретном экземпляре поле `Tags == nil`, тип всё равно несравним.
