# Горутины: жизненный цикл, планировщик, блокировки и утечки

## 1. Что создаётся при `go f()`

`go f()` создаёт независимый поток выполнения внутри процесса Go, **не** отдельный поток ОС. При этом функция и аргументы `f()` вычисляются в вызывающей горутине перед запуском новой (сам вызов `f` выполняется в новой горутине).

```go
func f(x int) { fmt.Println(x) }
func main() {
    x := 1
    go f(x) // аргумент вычислен как 1
    x = 2
    // Печать 1 НЕ гарантирована: main может завершиться раньше.
}
```

**Каверза:** `go f()` сам по себе не означает «f успела выполниться» и не создаёт happens-before от завершения `f` к следующей строке запускающей горутины.

## 2. GMP: зачем G, M и P

- **G** — объект горутины (состояние, стек, информация для планировщика).
- **M** — реальный поток ОС, исполняющий Go-код или находящийся в syscall.
- **P** — ресурс выполнения Go-кода и локальная очередь runnable goroutines.

Чтобы G исполнялась на CPU, M нужен P. Количество P ограничено `GOMAXPROCS`. Горутин может быть на порядки больше, чем M или P.

**Поведение:** `GOMAXPROCS(1)` ограничивает одновременное исполнение Go-кода, но не означает «только одна горутина существует»; блокировки на каналах позволяют планировщику переключаться на другие G.

## 3. Состояния: runnable / running / waiting / syscall

При ожидании канала, mutex, таймера горутина часто переходит в состояние ожидания и уступает P другим задачам. Она не крутится в цикле CPU, если оператор действительно блокирующий. При блокирующем системном вызове M может задержаться, и runtime передаст P другому M.

Netpoller позволяет типичному сетевому I/O ждать готовности дескриптора **без отдельного заблокированного потока на каждое соединение**.

**Каверза:** парковка G экономит CPU, **но не отменяет расход памяти**: стек, ссылки на объекты, дескрипторы и прочие ресурсы остаются. «Заблокированные горутины ничего не стоят» — миф.

## 4. Стек горутины и escape analysis

Стек начинается небольшим и может расти/сжиматься. Данные могут попасть в heap, если анализ выхода указывает, что они переживают локальный вызов. `new(T)`, указатель и замыкание сами по себе не дают универсального ответа «heap». Проверяй:

```bash
go build -gcflags="-m=2" ./...
go test -bench=. -benchmem ./...
```

Не полагайся на численные размеры стеков как на константы спецификации.

## 5. Порядок запуска и печати не определён

```go
var wg sync.WaitGroup
for i := 0; i < 3; i++ {
    wg.Add(1)
    go func(v int) {
        defer wg.Done()
        fmt.Print(v, " ")
    }(i)
}
wg.Wait() // порядок может быть 2 0 1, 0 1 2 и т.д.
```

`Wait()` гарантирует завершение зарегистрированных задач, но не порядок исполнения и не порядок выводов. `time.Sleep` — не корректный способ дождаться всех горутин.

## 6. Старый баг захвата переменной цикла и Go 1.22+

В модулях с `go 1.22` и новее переменные, объявленные `:=` в цикле, создаются заново для итераций. Поэтому старая загадка «все goroutines видят последнее i» **не универсальна**.

Но если переменная объявлена **до** цикла, она по-прежнему общая:

```go
var i int
for i = 0; i < 3; i++ {
    go func() { fmt.Println(i) }() // чтение i без синхронизации: race
}
```

Надёжнее явно передавать значение: `go func(v int){...}(i)`.

## 7. Data race vs логическая гонка

Data race — два обращения к одной памяти без нужного happens-before, хотя бы одно — запись. Результаты могут быть непредсказуемы. **Но отсутствие data race не гарантирует правильность алгоритма**.

```go
var counter atomic.Int64
// Атомарный счётчик корректен как отдельное число,
// но не защищает инвариант между счётчиком и обычной map.
```

Для пары полей, которые должны меняться вместе, лучше mutex или copy-on-write snapshot, а не два независимых атомика.

## 8. `panic` в дочерней горутине

`recover` работает только в отложенной функции **той же горутины**, в которой раскручивается panic. `recover` в родительской горутине не перехватит panic дочерней.

```go
go func() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("worker failed: %v", r)
        }
    }()
    runWorker()
}()
```

Поглощать panic без логирования и продуманной реакции опасно. `sync.WaitGroup.Go` (Go 1.25+) требует, чтобы переданная функция не паниковала.

## 9. Горутину нельзя «убить» извне

`context.Context` передаёт сигнал отмены, а не принудительно прерывает выполнение. Код должен сам обрабатывать `ctx.Done()` и использовать отменяемые API. Никакая `cancel()` не вынудит завершить бесконечный CPU-loop, не проверяющий сигнал, или операцию, ожидающую `ch <- value` без `select`.

```go
for {
    select {
    case job, ok := <-jobs:
        if !ok { return }
        process(job)
    case <-ctx.Done():
        return
    }
}
```

Если `process(job)` может долго блокироваться и игнорирует контекст, отмена будет задержана. Прокидывай `ctx` в операции (БД, HTTP и т.д.).

## 10. Утечки: горутина удерживает ресурсы

Классическая утечка: результат никому не нужен, но worker навсегда ждёт `out <- x`. Или воркер ожидает чтения из канала, который никто не закроет.

**Устранять конструктивно:** каждый `go`-вызов должен иметь понятное условие завершения, владельца отмены и механизм ожидания. В идеале lifetime ограничен родителем задачи (structured concurrency, `errgroup.WithContext` для группы воркеров).

Профилировать: `runtime/pprof`, goroutine dump, runtime trace; в Go 1.27 доступен специальный goroutine leak profiler (см. release notes).

## 11. Завершение main и background workers

`main` не ждёт все горутины автоматически. Как только `main` возвращается, процесс завершается и фоновые горутины прекращают исполняться, их `defer` не обязаны выполниться.

Для graceful shutdown: перестать принимать новые задачи, отменить или дождаться текущих, дождаться workers, закрыть owned resources, затем завершить `main`.

## 12. Лимитирование и backpressure

`go handle(req)` на каждый запрос без лимита может исчерпать память/БД/сокеты. `GOMAXPROCS` не ограничивает число одновременно **существующих** горутин. Используй bounded worker pool, semaphore, bounded queues и политику перегрузки.
