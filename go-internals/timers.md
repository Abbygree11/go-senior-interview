# `time.Timer`, `time.Ticker` и `time.After`: каналы, Stop/Reset, версии Go

## 1. Для чего предназначены

`time.NewTimer(d)` — однократное событие после указанной длительности; `time.NewTicker(d)` — периодические события; `time.After(d)` — удобный канал для однократного ожидания.

```go
timer := time.NewTimer(time.Second)
defer timer.Stop()
select {
case <-timer.C:
    fmt.Println("timeout")
case <-ctx.Done():
    return
}
```

**Важно:** наступление timeout не означает принудительное прерывание произвольного пользовательского кода. Оно означает доступность события таймера (а время выполнения горутины зависит от scheduler).

## 2. Go 1.23 и особенно Go 1.27 изменили поведение каналов таймеров

В современных реализациях таймерные каналы — синхронные (unbuffered). С Go 1.27 удалена прежняя обратная совместимость `asynctimerchan`: каналы пакета `time` всегда unbuffered, независимо от настройки модуля.

Старые вопросы «Stop обязательно нужно сопровождать drain канала таймера, иначе Reset прочтёт stale value» требуют указания **версии Go**. Для современных версий уже действуют более сильные гарантии `Stop/Reset` по отсутствию устаревших значений после успешного вызова; точный контракт смотри в документации конкретной версии.

## 3. `Stop` не закрывает `Timer.C`

`timer.Stop()` прекращает будущий сигнал таймера в соответствии с контрактом. **Он не закрывает канал `C`**. Поэтому `for range timer.C` не является корректным способом «читать до закрытия» — закрытия не будет.

То же важно для `Ticker.Stop()`: канал не закрывается, чтобы исключить ложные сигналы завершения.

## 4. `time.After` в цикле

```go
for {
    select {
    case <-jobs:
        work()
    case <-time.After(time.Second):
        tick()
    }
}
```

Каждая итерация создаёт новый таймер. В старых версиях Go это могло удерживать таймеры до их срабатывания даже при уходе по другой ветке. В современных Go (с Go 1.23) сборщик может собирать недостижимые неостановленные таймеры — но **постоянные аллокации** всё ещё могут быть лишней нагрузкой. Для периодики часто лучше один `Ticker` с явным `Stop`.

## 5. Точность таймаутов

Таймер не гарантирует точного момента выполнения callback/выдачи значения: scheduler, системные часы, нагрузка влияют на задержки. Для deadline операции используй `context.WithDeadline/WithTimeout` и API, действительно поддерживающие отмену.

## 6. Тесты с fake time / synctest

Тесты, полагающиеся на `time.Sleep(10 * time.Millisecond)` как на гарантию завершения горутин, flaky. Лучше каналы/WaitGroup, и где применимо — инструменты тестирования времени (например, `testing/synctest` в подходящих версиях Go).

## Дополнительные таймерные ловушки и версии

### 8. `Ticker.Stop()` не закрывает канал

```go
t := time.NewTicker(time.Second)
t.Stop()
// for range t.C { ... } // после Stop не получим «закрытие»
```

Остановка прекращает будущие ticks, но канал не закрывается. Если worker читает из ticker в цикле, ему нужен **отдельный stop/done/context**.

### 9. `time.After` в `select` с cancel

```go
select {
case <-time.After(5 * time.Second):
    return errors.New("timeout")
case <-ctx.Done():
    return ctx.Err()
}
```

Если обе ветки готовы в момент выбора, `select` может выбрать любую. Даже при `ctx.Err()!=nil` возможно получить собственную ошибку timeout вместо `ctx.Err`. Для последовательной политики обработки ошибок проверяй причину отмены отдельно, но строгая приоритетность требует продуманного протокола.

### 10. `Reset` и устаревшие buffered semantics

До Go 1.23 каналы таймеров обычно имели буфер ёмкости 1, из-за чего stale tick при `Reset` был распространённой ловушкой. С Go 1.23 (для модулей с соответствующей семантикой) каналы стали синхронными; Go 1.27 удалил обратную совместимость `asynctimerchan`, поэтому пакет `time` всегда использует unbuffered timer channels. **Не повторяй старые советы без версии Go**.

### 11. `time.AfterFunc` не предоставляет `Timer.C`

`time.AfterFunc(d, f)` вызывает callback в своей горутине после timeout; полученный `*Timer` не используется через обычный `C`. `Stop` и `Reset` для такого timer имеют собственную семантику (в том числе возможность конкурентного запуска callback после Reset). Нужна внешняя координация, если важно дождаться завершения callback.

### 12. `time.Sleep` и flaky tests

Сон на фиксированное число миллисекунд не гарантирует завершения другой горутины, особенно на загруженном CI. Для тестов надо ждать наблюдаемый сигнал через канал/WaitGroup либо использовать механизмы fake time/`testing/synctest` на подходящих версиях.
