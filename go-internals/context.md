# `context.Context`: дерево отмены, deadline, значения, утечки

## 1. Что это за объект

Интерфейс `Context` предоставляет `Deadline()`, `Done()`, `Err()`, `Value(key)`. Реализации связывают родителя и потомков; вызов `cancel` закрывает `Done()` дочернего контекста и распространяет отмену дальше.

**Важнейшее:** отмена кооперативна. Она **не убивает горутину** и не гарантирует, что уже начатая операция прекратится мгновенно. Она всего лишь даёт доступный для наблюдения сигнал.

## 2. `Background` и `TODO`

`context.Background()` и `context.TODO()` не отменяются автоматически: их `Done()` возвращает `nil`. Поэтому `<-context.Background().Done()` никогда не завершается.

`context.TODO()` — подсказка «здесь пока не определён правильный контекст», а не отменяемая альтернатива `Background`.

## 3. Дерево и deadlines

```go
parent, cancelParent := context.WithTimeout(context.Background(), 5*time.Second)
defer cancelParent()
child, cancelChild := context.WithTimeout(parent, 30*time.Second)
defer cancelChild()
```

Дочерний deadline не может сделать живучесть больше родительской: эффективное ограничение — раньше наступающее. Не создавай `WithTimeout` на каждый шаг с бессмысленным продлением, если общий запрос уже ограничен более жёстко.

## 4. Отмена vs завершение

```go
ctx, cancel := context.WithCancel(context.Background())
go func() {
    for {
        select {
        case <-ctx.Done():
            return
        default:
            work() // если зависнет, отмена сама его не разбудит
        }
    }
}()
cancel()
```

`cancel()` только сигнализирует; чтобы узнать, что горутина вышла, нужен `WaitGroup` или канал завершения, а `work` должно учитывать отмену/таймаут.

## 5. Отмена при отправке в канал

```go
select {
case out <- value:
case <-ctx.Done():
    return
}
```

Если обе ветки готовы, `select` может всё-таки выполнить send после отмены. **Context не является механизмом приоритетов или транзакционного запрета новых событий**. Нужен собственный протокол, если в системе строго запрещены поздние отправки.

## 6. `WithCancelCause`: причина отмены

`context.WithCancelCause` позволяет передать смысловую ошибку при отмене; `context.Cause(ctx)` возвращает причину. `ctx.Err()` при этом остаётся общим состоянием отмены (`context.Canceled` или `DeadlineExceeded`).

Для логирования причин и координации нескольких workers это часто полезнее, чем просто `cancel()`.

## 7. Почему всегда вызывать `cancel`

Даже если таймаут скоро истечёт, вызов `cancel` освобождает связанные ресурсы и связь дочернего контекста с родителем раньше. Канонично `ctx, cancel := context.WithTimeout(...); defer cancel()`.

## 8. `Value` не для произвольных параметров

`ctx.Value` предназначен для **request-scoped metadata**, которые пересекают границы API (trace ID и подобное), а не для передачи обязательных параметров или глобального mutable state. Используй собственные несравнимые по имени типы ключей, не простые общедоступные строки, чтобы не было коллизий.

## 9. Контекст и HTTP/SQL

Прокидывай `ctx` в `http.NewRequestWithContext`, `QueryContext` / `ExecContext` / `BeginTx`. Но гарантия конкретного завершения зависит от поведения сервера, драйвера, сети и операции. Установка контекста не превращает любой произвольный код в отменяемый.

## 10. Утечки через `WithTimeout` в горячем цикле

Создавать новые дочерние контексты, не вызывая `cancel`, может задержать освобождение таймеров/ссылок. Не делай `defer cancel()` внутри многотысячного цикла одной функции: все отложенные вызовы выполнятся только при выходе из функции. Выдели отдельную функцию на итерацию или вызывай `cancel` явно в каждой ветке.
