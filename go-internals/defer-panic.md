# `defer`, `panic`, `recover`: порядок, аргументы, замыкания, ресурсы

## 1. Время регистрации и время вызова

`defer f(arg)` немедленно вычисляет функцию-получатель и **аргументы**, но откладывает само выполнение `f` до завершения окружающей функции. Defer исполняются в порядке LIFO (последний зарегистрирован — первый выполнен).

```go
func f() {
    x := 10
    defer fmt.Println(x)
    x = 20
}
func main() { f() } // 10
```

Получатель метода тоже вычисляется при регистрации. Поэтому `defer file.Close()` закрывает **тот файл, значение которого было получено тогда**, даже если переменная `file` потом переназначена.

## 2. Замыкание читает захваченную переменную позже

```go
func f() {
    x := 10
    defer func() { fmt.Println(x) }()
    x = 20
}
func main() { f() } // 20
```

Если значение нужно зафиксировать при регистрации, передай его аргументом замыкания: `defer func(v int){ fmt.Println(v) }(x)`.

## 3. LIFO

```go
func f() {
    defer fmt.Println(1)
    defer fmt.Println(2)
    defer fmt.Println(3)
}
func main() { f() }
// 3
// 2
// 1
```

## 4. Именованные результаты: defer меняет итог возврата

```go
func f() (result int) {
    defer func() { result += 10 }()
    return 5
}
fmt.Println(f()) // 15
```

Механика: `return 5` присваивает именованному `result` значение 5, затем выполняются defer, затем функция возвращает окончательное значение. Для неименованного результата нельзя просто изменить `result`, если такого параметра нет.

**Каверза:** ошибки можно непреднамеренно заменить в defer; но правильно написанная отложенная функция может обработать ошибку `Close` и объединить её с уже существующей (например, `errors.Join`).

## 5. `defer` внутри цикла привязан к функции, а не к итерации

```go
for _, path := range paths {
    f, err := os.Open(path)
    if err != nil { return err }
    defer f.Close() // закроется только при выходе из ВНЕШНЕЙ функции
}
```

При большом числе файлов можно исчерпать fd. Простые фигурные скобки `{}` не помогают; нужен отдельный **вызов функции** на итерацию или явное закрытие на всех путях.

```go
func process(path string) error {
    f, err := os.Open(path)
    if err != nil { return err }
    defer f.Close()
    return use(f)
}
for _, path := range paths {
    if err := process(path); err != nil { return err }
}
```

## 6. `panic`: вызовы defer при раскрутке стека

Обычная panic начинает раскручивать стек текущей горутины, исполняя defer на выходе из функций. `recover` может остановить её **только при непосредственном вызове из отложенной функции той же горутины**.

```go
func safe() {
    defer func() {
        if x := recover(); x != nil {
            fmt.Println("caught:", x)
        }
    }()
    panic("boom")
}
```

`recover` во внешней родительской горутине не ловит panic дочерней. `os.Exit` завершает процесс без выполнения defer. Фатальные ошибки runtime, например обнаруженная concurrent map misuse, не стоит путать со штатными recoverable panic.

## 7. `defer` и nil-значения

```go
var f *os.File
defer f.Close() // receiver вычислен как nil; при выполнении возможна ошибка/паника
```

Не объявляй `defer file.Close()` до проверки успешного открытия файла. Для методов с nil receiver поведение зависит от реализации метода, поэтому конкретный результат не универсален. Для `(*os.File).Close` nil receiver возвращает ошибку, но не рассчитывай на это для любого типа.

## 8. `defer` и стоимость

В современном Go `defer` существенно оптимизирован, особенно в простых случаях. Микрооптимизация «ручной Unlock всегда быстрее defer» устарела как универсальное правило; измеряй бенчмарками. Выбирай корректность и гарантированный cleanup, учитывая, что отложенные функции в длительном цикле накапливаются до выхода из функции.

## 9. `Close` может возвращать ошибку

`defer f.Close()` игнорирует ошибку закрытия. Это может быть допустимо для некоторых read-only ресурсов, но при записи иногда важно проверять ошибку flush/close:

```go
func writeFile(f *os.File) (err error) {
    defer func() {
        err = errors.Join(err, f.Close())
    }()
    _, err = f.WriteString("data")
    return err
}
```

Важно понимать: `errors.Join(nil, nil) == nil`, а если оба вызова неуспешны, информация об обоих сохраняется.
