# `sync.Map`: API, шаблоны нагрузки, атомарные операции и ловушки

## 1. Зачем отдельный тип

Обычная `map[K]V` не допускает конкурентную запись/чтение без внешней синхронизации. `sync.Map` предоставляет операции с встроенной синхронизацией и оптимизации под специфические сценарии: **ключи записываются один раз и многократно читаются** либо горутины работают с преимущественно непересекающимися наборами ключей.

Внутренняя реализация `sync.Map` может иметь быстрый read-mostly путь и дополнительные структуры для изменяемых записей, но **не нужно фиксировать конкретное число внутренних map как API-контракт**: реализация меняется между версиями.

## 2. API отличается от обычной map

```go
var m sync.Map
m.Store("x", 1)
v, ok := m.Load("x")
fmt.Println(v, ok) // 1 true
m.Delete("x")
```

Ключи и значения имеют тип `any`, поэтому компилятор не обеспечит, что `Load` вернул именно `int`. Нужна проверка типа или тонкая generic-обёртка с гарантиями на границе API.

## 3. `Load` + `Store` не атомарны как пара

```go
v, _ := m.Load("count")
m.Store("count", v.(int)+1) // два workers могут потерять инкремент
```

Даже если каждый `Load` и `Store` корректен конкурентно, их комбинация не образует транзакцию. Для инициализации используй `LoadOrStore`; для условного обновления — `CompareAndSwap`, если подходят требования к сравнимости значения. Для сложной групповой логики удобнее `map + Mutex`.

## 4. `LoadOrStore` при конкуренции

```go
actual, loaded := m.LoadOrStore("key", expensiveResult())
```

**Каверза:** `expensiveResult()` выполняется **до вызова** `LoadOrStore`. Если два workers вызывают строку одновременно, оба могут построить дорогое значение, хотя сохранится одно. `LoadOrStore` предотвращает дублирование **записи**, не дублирование вычислений.

Если вычисление дорого и должно выполняться ровно один раз — храни `*entry` с `sync.Once` (или используй `singleflight`).

## 5. `Range` — не consistent snapshot

`Range` может обходить карту при конкурентных изменениях, но не обещает согласованную фотографию всех записей в один момент времени. Модификации других горутин могут наблюдаться неравномерно; каждое ключевое значение посещается согласно контракту API, но набор представленных данных не является транзакцией.

Код, который на основе `Range` вычисляет точный суммарный баланс или глобальный инвариант, может быть некорректен без дополнительной координации.

## 6. Производительность не универсальна

При множественных перезаписях одного ключа и строгом типизированном API `map + RWMutex` может быть быстрее/проще. При постоянном добавлении новых ключей тоже стоит измерить. Benchmarks на реальном распределении ключей и read-write ratio важнее слогана «sync.Map быстрее на чтениях».

## 7. Копирование, nil и очистка

`sync.Map` готов к использованию как zero value. Копировать `sync.Map` после начала использования нельзя. `Clear` удаляет записи, но не даёт полного протокола барьера для параллельных обращений как «теперь все workers точно видят пустую map» без анализа конкретных взаимодействий.
