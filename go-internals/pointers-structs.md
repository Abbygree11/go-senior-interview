# Указатели и структуры Go: копирование, aliasing, receiver, nil и layout

## 1. Структура — значение

`struct` содержит поля как единое значение. Присвоение `b := a` копирует поля. Но если поле само указывает на общий объект (`slice`, `map`, `*T`, интерфейс с указателем внутри), копирование поля **не делает глубокую копию**.

```go
type User struct {
    Name string
    Tags []string
}
a := User{Name: "A", Tags: []string{"x"}}
b := a
b.Name = "B"
b.Tags[0] = "y"
fmt.Println(a.Name, a.Tags) // A [y]
```

Различай **копирование самой структуры** и **копирование объектов за ссылкоподобными полями**.

## 2. Pointer vs value receiver

```go
type Counter struct{ N int }
func (c Counter) IncCopy() { c.N++ }
func (c *Counter) Inc()    { c.N++ }
func main() {
    c := Counter{}
    c.IncCopy()
    fmt.Println(c.N) // 0
    c.Inc()
    fmt.Println(c.N) // 1
}
```

Value receiver копирует структуру. Pointer receiver работает через адрес исходного значения. У больших структур или структур с `sync.Mutex` обычно нужны pointer receivers.

## 3. Указатель можно передать, но это не deep-copy

`p2 := p1` копирует значение адреса, а не объект. Запись `p2.Field = x` затрагивает объект по тому же адресу. Если разные goroutines используют `p1` и `p2`, это **общее** состояние и ему может понадобиться синхронизация.

## 4. Nil pointer receiver: вызов может быть допустим

```go
type Node struct{ Next *Node }
func (n *Node) IsNil() bool { return n == nil }
var n *Node
fmt.Println(n.IsNil()) // true
```

Вызов метода с `*Node` receiver возможен, пока метод умеет работать с nil. `n.Next` при nil вызовет panic. Значит «метод на nil всегда паникует» неверно. При этом для **value receiver** вызов через nil pointer требует разыменования значения и обычно паникует.

## 5. Method sets и интерфейсы

Если `func (*T) M()`, интерфейс, требующий `M()`, реализует `*T`, но не `T`. `t.M()` иногда компилируется для адресуемого `t` благодаря автоматическому взятию адреса, но это **не расширяет method set самого `T`**.

## 6. Не копировать lock после использования

```go
type Safe struct {
    mu sync.Mutex
    m  map[string]int
}
// func (s Safe) Set(...) {} // опасно: receiver копирует mutex
```

Если значения `Safe` копируются, mutex в копиях **разные**, а внутренние `m` могут быть общими. Это разрушает защиту даже при правильных `Lock/Unlock` в каждом методе.

## 7. Выравнивание и padding

Размер структуры обычно включает padding для alignment полей, поэтому сумма `unsafe.Sizeof` полей не обязательно равна размеру всей структуры. Порядок полей иногда влияет на размер/число cache lines.

Не строй протокол хранения/сетевой формат на «сыром layout struct»: он зависит от архитектуры, типов и может меняться. Для форматов передачи применяй явную сериализацию.

## 8. `new`, `make`, escape analysis

`new(T)` создаёт значение T и возвращает `*T`; `make` используется для инициализации slice/map/channel. Наличие указателя не гарантирует размещение в куче. Начиная с Go 1.26 `new(expr)` поддерживает выражение и создаёт указатель на новое значение, инициализированное этим выражением.

```go
p := new(123) // Go 1.26+: *int со значением 123
fmt.Println(*p) // 123
```

В старых версиях Go `new(123)` не компилируется: там операндом должен был быть тип.

## 9. Указатель на элемент map нельзя взять

`&m[key]` не компилируется: элементы map не адресуемы. `&s[i]` для слайса допустим, если индекс корректен. Указатель на элемент слайса может продолжать указывать на **старый backing array** после `append` с перевыделением: не думай, что он автоматически перенаправится на новый слайс.
