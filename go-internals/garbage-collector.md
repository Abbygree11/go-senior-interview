# Память и GC: escape analysis, трёхцветная маркировка, Green Tea, удержание объектов

## 1. Стек и heap — следствие анализа, не синтаксиса

Компилятор решает, может ли объект храниться на стеке либо обязан жить в heap, чтобы пережить текущий вызов. `new(T)` не значит автоматически «аллоцировать в heap». Возврат указателя часто ведёт к escape, но оптимизация/инлайнинг могут исключать отдельные аллокации.

```bash
go build -gcflags="-m=2" ./...
go test -bench=. -benchmem ./...
```

Измерять конкретный hot path; не делать выводы о расположении только по наличию указателя.

## 2. Что достижимо и что собирается

GC отслеживает достижимость объектов от корней (стеков, глобальных ссылок и др.). Циклические ссылки **не являются утечкой сами по себе**: если цикл больше недостижим, его память может быть собрана.

GC не обещает освободить объект немедленно после последнего использования и не гарантирует немедленный возврат освобождённой памяти ОС.

## 3. Трёхцветная модель и write barriers

В теоретической модели: белые объекты ещё не отмечены, серые найдены, но требуют сканирования, чёрные просканированы. Модификация графа ссылок параллельно с маркировкой требует write barriers, чтобы новый reachable объект не потерялся.

**Важно:** это понятная модель алгоритма, а не гарантия, что каждая оптимизация конкретной версии runtime буквально реализует указанные цвета как явные поля.

## 4. Что изменилось в Go 1.26: Green Tea GC

Начиная с Go 1.26 по умолчанию используется Green Tea GC, оптимизирующий локальность и сканирование небольших объектов; в Go 1.25 он был экспериментальным. Это изменение внутренней реализации, а не новый контракт владения памятью. Оценка производительности должна опираться на конкретный workload.

## 5. Гигантский backing array удерживается мелким слайсом

```go
func head(big []byte) []byte {
    return big[:16] // backing array может оставаться достижимым целиком
}
```

Вызвавший код держит 16 байт «логически», а в heap может оставаться огромный массив. Сделай `bytes.Clone(big[:16])`, если нужно отделить память.

`slices.Clip` не является клонированием и не гарантирует освобождения старого backing array.

## 6. Удаление из слайса ссылочных значений

`s = append(s[:i], s[i+1:]...)` уменьшает длину, но ссылки за новым `len` могут оставаться в backing array и удерживать объекты. Когда это важно, обнуляй хвост или используй современный `slices.Delete` (в актуальных версиях он обнуляет ненужный хвост). Не обнуляй без анализа aliasing.

## 7. `sync.Pool` и GC

`sync.Pool` не гарантирует сохранение объектов: runtime вправе удалять элементы в любое время, в том числе во время GC. Это средство уменьшения аллокаций для временных объектов, **не кэш с гарантиями**. После `Put` объект может получить другая горутина; нельзя продолжать использовать его как эксклюзивно свой.

## 8. `GOGC`

`GOGC` определяет ориентир роста кучи относительно объёма живых данных (и связанных с ними корней) до следующего цикла GC. Меньшее значение часто уменьшает пиковое потребление памяти ценой большего GC CPU; большее — обратный компромисс. Это **не** простое «GC каждые N миллисекунд».

## 9. `GOMEMLIMIT`

Мягкий лимит памяти, контролируемой runtime; **не жёсткая граница RSS всего процесса**. Внешние аллокации, cgo, фрагментация, stack/OS и другие факторы могут привести к OOM даже с установленным лимитом. Слишком низкий лимит может вызвать чрезмерную работу GC без решения основной проблемы.

## 10. Finalizers и cleanup

Не полагайся на финализаторы для своевременного освобождения fd/транзакций/сетевых соединений. Выполнение финализатора может задержаться или не произойти до завершения процесса. Нужны явные `Close`, `Rollback`, shutdown и `defer` в контролируемой области выполнения.

## 11. Heap profile: почему большая heap ≠ утечка

Высокий график heap может означать рабочий кэш, временные аллокации и ещё не выполненный GC. Сравни `inuse_space` (живое) и `alloc_space` (сумма аллокаций), учти текущую нагрузку и retention paths. Pprof нужен для **поиска причины**, а не для уверенного диагноза по одному числу.
