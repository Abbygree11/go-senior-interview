# Атомарные операции (`sync/atomic`): CAS, порядок памяти, ABA, `atomic.Value`

## 1. Что именно атомарно

Операция `Load`, `Store`, `Add`, `Swap` или `CompareAndSwap` над поддерживаемым атомарным значением выглядит для других горутин как **неделимый шаг**. В отличие от `x++` (чтение → сложение → запись), `atomic.Int64.Add(1)` не теряет конкурентные инкременты.

Современный типизированный API:

```go
var n atomic.Int64
n.Store(10)
fmt.Println(n.Add(5))           // 15
fmt.Println(n.Load())           // 15
fmt.Println(n.CompareAndSwap(15, 20)) // true
fmt.Println(n.Load())           // 20
```

Типизированные атомики (`atomic.Int32`, `Int64`, `Bool`, `Pointer[T]`, `Uint64` и т. д.) проще использования старого API с указателями. Атомарные объекты нельзя копировать после начала использования.

## 2. Семантика памяти: sequential consistency

Go atomic memory model использует **последовательно согласованные (sequentially consistent)** операции. Их можно рассматривать как исполняющиеся в некотором едином глобальном порядке, согласованном с порядком программы; если эффект атомарной операции A замечен атомарной операцией B, между ними есть соответствующая синхронизация.

На реальных CPU для этого используются аппаратные атомарные инструкции и/или барьеры; детали зависят от архитектуры. **Не путать** последовательную согласованность атомиков с магической атомарностью всей бизнес-операции.

## 3. Атомарный счётчик != транзакция

```go
var a, b atomic.Int64
func write() {
    a.Store(1)
    b.Store(1)
}
func read() (int64, int64) {
    return a.Load(), b.Load()
}
```

Читатель может увидеть `(1, 0)`: хотя все отдельные операции атомарны, пара из двух полей **не обновляется атомарно**. Нужны mutex или публикация одного неизменяемого snapshot.

## 4. CAS: сравни и обменяй

`CompareAndSwap(old,new)` выполняет замену, только если текущее значение равно `old`, и сообщает, удалось ли это. Он нужен для optimistic concurrency:

```go
var x atomic.Int64
func increment() {
    for {
        old := x.Load()
        if x.CompareAndSwap(old, old+1) {
            return
        }
    }
}
```

Для простого инкремента `Add(1)` предпочтительнее. **Каверза**: CAS может многократно проигрывать при конкуренции, и цикл может быть горячим по CPU. Lock-free не означает wait-free, отсутствие голодания или всегда лучшую производительность.

## 5. ABA problem

Допустим, поток 1 читает указатель `A` и собирается выполнить CAS. Поток 2 меняет значение `A → B → A`. CAS первого потока может **успешно** сравнить с A и не заметить промежуточных переходов, хотя логический объект/его поколение уже изменился.

При работе с lock-free структурами нужно рассматривать версии/поколения, владение памятью, snapshot или переход на mutex. В Go GC не решает **логическую** ABA-проблему (даже когда память управляется безопасно).

## 6. `atomic.Pointer[T]`: публикация неизменяемого снимка

```go
type Config struct {
    Host string
    Limits map[string]int
}
var current atomic.Pointer[Config]
func publish(host string, limits map[string]int) {
    clone := maps.Clone(limits)
    current.Store(&Config{Host: host, Limits: clone})
}
func read() {
    cfg := current.Load()
    if cfg == nil { return }
    fmt.Println(cfg.Host)
}
```

`Store` атомарно заменяет **указатель**, но **не делает потокобезопасными записи** в `cfg.Limits`. Важное правило: после публикации snapshot никто не изменяет его содержимое. Даже `maps.Clone` — поверхностная копия; если значения — указатели, их нужно изолировать отдельно.

## 7. `atomic.Value`: динамический тип и panic

`atomic.Value` хранит значение любого конкретного типа, но первый `Store` задаёт его динамический тип. Последующие `Store` должны иметь **точно такой же конкретный тип**. `Store(nil)` вызывает panic; `Load` до первого `Store` возвращает `nil`.

```go
var v atomic.Value
fmt.Println(v.Load() == nil) // true
v.Store("hello")
fmt.Println(v.Load())       // hello
// v.Store(1)              // panic: другой concrete type
// v.Store(nil)            // panic
```

`atomic.Value` подходит для immutable config. Если внутри лежит `map` или `[]T`, атомарно загружается лишь значение интерфейса, а не замораживается объект. Обновление через `Load→изменить map→Store` **не является атомарной транзакцией**.

## 8. Смешивать обычные и atomic обращения нельзя

```go
var n int64
go func() { atomic.AddInt64(&n, 1) }()
fmt.Println(n) // ПЛОХО: обычное чтение конкурентно с атомарной записью
```

Читай через `atomic.LoadInt64(&n)` и записывай атомарно. Нельзя объявить переменную «условно защищённой» из-за того, что писатель использовал atomic: все конкурентные обращения должны соблюдать контракт.

## 9. Выравнивание и копирование

Старые функции `atomic.*Int64` на некоторых 32-битных архитектурах предъявляют требования к 64-битному выравниванию. Типизированные `atomic.Int64`/`Uint64` упрощают переносимость. Не копируй атомарные объекты после использования; при вложении в структуру выбирай pointer receivers.

## 10. `atomic.Bool` как флаг отмены

```go
var stopped atomic.Bool
go func() {
    for !stopped.Load() {
        doOneStep()
    }
}()
stopped.Store(true)
```

Флаг может работать для простого polling, но **не прерывает блокирующий syscall или `ch <- x`**. Для отмены ожидания канала/сети обычно лучше контекст и cancellable APIs. Цикл без работы/ожидания может быть busy spin.

## 11. Atomics vs `sync.Mutex`

Используй атомики, если модель состояния очень проста и ты явно понимаешь инварианты. Для нескольких взаимозависимых полей и сложных модификаций `Mutex` обычно легче доказать корректным. Не выбирай atomics по догме «без lock быстрее»: ложное разделение cache lines, CAS contention и сложный retry-путь могут проигрывать mutex.
