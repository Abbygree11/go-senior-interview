# Go Memory Model: happens-before, data race и публикация данных

## 1. Зачем вообще нужна модель памяти

В многопоточной программе вопрос не только «кто раньше выполнил строку», но и «когда запись становится наблюдаемой другой горутиной». Компилятор и CPU могут оптимизировать порядок операций, если программа не обеспечила требуемой синхронизации. В Go память описывается отношениями **sequenced-before**, **synchronized-before** и их транзитивным замыканием **happens-before**.

Data race: конфликтующие обращения к одной области памяти без необходимого порядка, хотя бы одно — запись (и это не надлежащие атомарные операции).

## 2. `go f()` не означает «f уже закончилась»

```go
var x int
go func() { x = 1 }()
fmt.Println(x) // data race, произвольное расписание
```

Нельзя исправить `time.Sleep(time.Second)`: сон не создаёт happens-before. Правильно — дождаться результата через канал или `WaitGroup`.

## 3. Канал публикует данные

```go
type Data struct{ X int }
func main() {
    ch := make(chan struct{})
    var d Data
    go func() {
        d.X = 42
        close(ch)
    }()
    <-ch
    fmt.Println(d.X) // 42, если других конкурентных записей нет
}
```

Закрытие синхронизируется с приёмом, который наблюдает закрытие, поэтому запись `d.X` предшествует чтению после `<-ch`. Это не значит, что **любая** произвольная операция с любым каналом заменяет синхронизацию другого общего объекта.

## 4. Buffered vs unbuffered: порядок не одинаков

Отправка синхронизируется с завершением **соответствующего приёма**. Для небyферизованного канала завершение приёма синхронизируется с завершением отправки. Для буферизованного канала отправитель может завершить отправку до того, как получатель вообще начнёт читать; полагаться на симметричную связь «receive → завершение send» здесь нельзя.

## 5. Mutex и видимость

```go
mu.Lock()
shared = 10
mu.Unlock()

// В другой горутине:
mu.Lock()
fmt.Println(shared)
mu.Unlock()
```

При условии, что другие писатели тоже используют тот же `mu`, чтение согласовано с предшествующими записями. **Важно**: использование разных mutex для одного shared поля не обеспечивает тот же порядок.

## 6. Атомики и публикация

`atomic.Store` / `Load` в Go имеют sequential consistency. Пример флага готовности:

```go
var ready atomic.Bool
var data int
go func() {
    data = 99
    ready.Store(true)
}()
for !ready.Load() {
    runtime.Gosched()
}
fmt.Println(data) // 99, если data больше никто конкурентно не пишет
```

Это допустимый пример **публикации** благодаря атомарному флагу; но циклический polling с `Gosched` не всегда лучший дизайн. Для ожидания готовности обычно удобнее канал.

## 7. Почему race detector не доказывает отсутствие гонок

`go test -race` инструментирует исполнявшиеся ветви. Если редкий сценарий не был воспроизведён, отчёта может не быть. Race detector выявляет **гонки памяти**, но не все логические ошибки: например, два атомарных списания с отдельными Load/Store могут потерять обновление без data race.

## 8. Почему «не падает» не значит «правильно»

Случайное взаимное расписание может годами скрывать race. Компилятор, архитектура CPU и нагрузка меняют воспроизведение. Корректный критерий — доказанный happens-before на всех путях, а не стабильный вывод в десяти тестовых запусках.
