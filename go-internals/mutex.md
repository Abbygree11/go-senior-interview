# `sync.Mutex`: блокировка, видимость памяти, тонкости использования

## 1. Что он защищает

`sync.Mutex` — взаимное исключение: в один момент защищённый участок выполняет не более одного владельца блокировки. В текущем runtime быстрый путь пытается захватить состояние атомарно, а при конкуренции используется ожидание/пробуждение; **точные биты, пороги и очереди не часть API**.

Ключевое — **happens-before**: n-й `Unlock` синхронизируется с более поздним успешным `Lock` по правилам документации; данные, записанные под lock, становятся согласованно видны следующему владельцу.

```go
type SafeCounter struct {
    mu sync.Mutex
    n  int
}
func (c *SafeCounter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}
func (c *SafeCounter) Get() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.n
}
```

Важно защищать **все** обращения, включая чтение. Только mutex у писателя, но без защиты у читателя — всё ещё data race.

## 2. Zero value готов к использованию

`var mu sync.Mutex` — корректно, специальной инициализации не требуется. `Lock` может вызывать одна горутина, а `Unlock` — другая: mutex Go **не привязан к идентичности горутины**, хотя такой протокол нужно очень аккуратно обосновывать.

## 3. Mutex не реентерабелен

```go
mu.Lock()
mu.Lock() // ждёт, пока кто-то Unlock, но эта же горутина до Unlock не дойдёт
```

В Go нет автоматической рекурсивной блокировки. Вызов метода, берущего тот же `mu`, из другой критической секции — частый скрытый deadlock.

## 4. `Unlock` незахваченного mutex

Это **фатальная ошибка runtime**, а не штатное значение `error`. Защищай инвариант «ровно один unlock после каждого успешного lock». `defer mu.Unlock()` сразу после захвата помогает, но не исправляет ошибку в управлении владением.

## 5. Копирование mutex после первого использования

```go
type Cache struct {
    mu sync.Mutex
    m  map[string]string
}
func (c Cache) Set(k, v string) { // ПЛОХО: receiver копирует mutex
    c.mu.Lock()
    defer c.mu.Unlock()
    c.m[k] = v
}
```

Разные копии `mu` могут защищать **одну и ту же map** — ложное чувство синхронизации. Используй `func (c *Cache) Set`; не копируй структуру с mutex после начала использования. Проверка: `go vet -copylocks ./...`.

## 6. `Lock` не поддерживает context

`mu.Lock()` нельзя напрямую прервать через `ctx.Done()`. Если нужна отмена ожидания lock, пересмотри архитектуру: меньшее время критической секции, передача владения, очередь, API `TryLock` (выполнить одну неблокирующую попытку, а не гарантировать справедливое ожидание).

`TryLock` часто признак сложного дизайна. Не делай busy-loop `for !mu.TryLock() {}` — это может сжечь CPU.

## 7. Порядок и справедливость

Не полагайся на порядок пробуждения или «горутинa, которая первой захотела, первой получит lock». Runtime имеет механизмы борьбы с голоданием, но Go не обещает прикладного FIFO. Не используй mutex в качестве планировщика задач.

## 8. Держать mutex во время медленного I/O — часто ошибка

```go
mu.Lock()
resp, err := client.Do(req) // может ждать сеть секунды
mu.Unlock()
```

Все остальные горутины, которым нужен этот mutex, стоят. По возможности копируй нужные данные под lock, отпускай lock, выполняй медленную операцию отдельно; при записи назад проверь, что состояние не поменялось (версия, optimistic concurrency).

Не делай callbacks в неизвестный пользовательский код под mutex — callback может снова запросить тот же lock.

## 9. Двойная проверка и инициализация

```go
if value == nil { // race, если value конкурентно читают/пишут
    mu.Lock()
    if value == nil { value = create() }
    mu.Unlock()
}
```

Обычное внешнее чтение переменной не становится безопасным от внутреннего lock. Используй `sync.Once`, atomic publication или защищай всё чтение.

## 10. Два mutex и порядок захвата

```go
// Горутина 1: lock(A) → lock(B)
// Горутина 2: lock(B) → lock(A)
// Возможен deadlock.
```

Для нескольких mutex договорись о глобальном порядке захвата. Для очень сложных инвариантов часто проще **один lock**, чем «сверхпараллельная» система с тонкими гонками.

## 11. Mutex vs channel vs atomics

- Mutex для совместной мутации нескольких полей и инвариантов.
- Канал для передачи работы/владения и протокола взаимодействия.
- Atomic для простых отдельных полей или immutable snapshots; не заменяет транзакцию над структурой.
- `RWMutex` стоит испытывать на read-mostly нагрузке, но не считать автоматически быстрее.

## 12. Диагностика

`go test -race` для гонок; mutex/block profiles через `pprof` для конкуренции за блокировки. Race detector не обязан находить deadlock. Контрольные вопросы: что означает happens-before после `Unlock`, почему `Cache.Set` с value receiver опасен, может ли другой worker вызывать `Unlock` и почему рекурсивный `Lock` зависает?

## Дополнительные tricky cases

### 13. `TryLock` не приоритет и не гарантия прогресса

`mu.TryLock()` (Go 1.18+) делает однократную попытку захвата. `false` значит «не получилось сейчас», а не «кто-то обязательно держал mutex на протяжении всей операции». `for !mu.TryLock() {}` может занять CPU и ухудшить справедливость.

### 14. Переиспользование копии lock — скрытая ошибка в методе

```go
type Counter struct { mu sync.Mutex; n int }
func (c Counter) Inc() { // КОПИЯ mu, n
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}
```

Здесь изменяется `c.n` внутри **локальной копии**, исходный `Counter` не изменится; при наличии map-полей случай опаснее, потому что разные копии mutex защищают **одну** map. Используй `*Counter` и `go vet -copylocks`.

### 15. Проверка вне lock разрушает инвариант

```go
if !stopped { // data race, если stopped меняется под mu
    mu.Lock()
    work()
    mu.Unlock()
}
```

Даже если `work()` защищена, начальное чтение общего флага без синхронизации не безопасно. Для инварианта «не выполнять работу после stopped» проверка `stopped` тоже должна быть **внутри** критической секции.

### 16. `defer Unlock` на горячем пути — не универсальный антипаттерн

Современный компилятор оптимизирует обычные `defer`. Удаление `defer` из коротких функций может ввести ошибку на раннем `return` и не дать измеримого выигрыша. Сравни бенчмарком, а не руководствуйся старым интервью-мифом «defer всегда медленный».

### 17. Блокировка не принадлежит горутине

Одна goroutine может `Lock`, другая `Unlock` — Go допускает это как свойство примитива. Но это повышает требования к протоколу владения: нельзя просто считать «Unlock вызывается там же, где Lock» аппаратной гарантией. Для обычного кода держи пару рядом, если нет обоснованной передачи владения.
