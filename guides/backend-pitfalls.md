# Go Backend: ошибки вокруг concurrency, сети и ресурсов

## 1. `context.Context`
**Устройство.** Несёт сигнал отмены, deadline и request-scoped values. Отмена распространяется к дочерним контекстам.
**Каверза.** `cancel()` **не останавливает горутину насильно** и не ждёт её завершения; блокирующий `ch <- x` не «просыпается» сам.
**Защита.** `select` с `ctx.Done()`, `WaitGroup` для ожидания завершения.

## 2. Deadline vs timeout
**Устройство.** Deadline — момент времени; timeout — относительная длительность. Родительский deadline ограничивает дочерний.
**Каверза.** Создание `WithTimeout` не гарантирует, что все операции завершатся к сроку, если они игнорируют контекст.
**Защита.** Прокидывать `ctx` в операции, настраивать сетевые таймауты; всегда вызывать `cancel` для освобождения ресурсов.

## 3. `http.Client` и `http.Transport`
**Устройство.** Клиент/транспорт предназначены для повторного использования и поддерживают пул соединений.
**Каверза.** Создание нового transport для каждого запроса мешает переиспользованию соединений. Отсутствие timeout/deadline может держать запрос долго.
**Защита.** Переиспользовать client; задавать timeouts осознанно по фазам и задачам.

## 4. HTTP response body
**Устройство.** `Response.Body` — ресурс, который должен закрыть вызывающий код.
**Каверза.** Если не закрывать body, можно утекать соединениями/ресурсами. Для повторного использования keep-alive часто важно дочитать тело до EOF; простого `Close` не всегда достаточно.
**Защита.** `defer resp.Body.Close()` после проверки err; разумные лимиты чтения.

## 5. HTTP server timeouts
**Устройство.** `http.Server` поддерживает `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`.
**Каверза.** Отсутствие лимитов делает сервер уязвимым к зависшим/медленным соединениям; значения требуют оценки с учётом streaming и long polling.
**Защита.** Настраивать с учётом характера API.

## 6. `database/sql` — это пул
**Устройство.** `*sql.DB` — потокобезопасный управляющий пулом, не одно физическое соединение.
**Каверза.** Создавать DB на каждый запрос не нужно; открытые `Rows` удерживают соединение и могут исчерпать пул.
**Защита.** Переиспользовать DB; `defer rows.Close()`, проверять `rows.Err()`.

## 7. Транзакции
**Устройство.** `*sql.Tx` привязана к одному соединению, транзакцию нужно завершить `Commit` или `Rollback`.
**Каверза.** Забытый rollback на ошибке удерживает ресурс; `defer tx.Rollback()` после Begin обычно безопасен даже после успешного Commit (но его ошибка уже не нужна).
**Защита.** Проверять ошибку Commit, не считать его гарантированным успехом по отсутствию ошибок предыдущих запросов.

## 8. `time.Ticker`, timers
**Устройство.** Периодические уведомления и таймеры — отдельные runtime-механизмы.
**Каверза.** В старых версиях Go поведение каналов таймеров и GC отличалось; устаревшие примеры про обязательную утечку `time.After` безоговорочно не переносить на новые версии.
**Защита.** Учитывать версию Go, явно останавливать timer/ticker, когда требуется прекратить уведомления, и тестировать.

## 9. Errors и wrapped errors
**Устройство.** `fmt.Errorf("%w", err)` сохраняет цепочку ошибок для `errors.Is` и `errors.As`.
**Каверза.** Сравнение с `==` wrapped error может не сработать. Прямое форматирование `%v` не поддерживает unwrap-семантику.
**Защита.** `errors.Is/As`; не использовать текст ошибки как машинный идентификатор.

## 10. `defer Close` и ошибки
**Устройство.** `Close()` нередко возвращает `error`.
**Каверза.** `defer f.Close()` игнорирует ошибку закрытия; при записи некоторые сбои проявляются именно при flush/close.
**Защита.** Явно обработать ошибку закрытия там, где важна долговечность записи.

## 11. `pprof`, tracing и race detector
**Устройство.** CPU/heap/goroutine/block/mutex-профили показывают разные классы проблем; race detector инструментирует обращения к памяти.
**Каверза.** Высокий CPU не всегда = GC; большая heap ≠ утечка; нет отчёта race ≠ нет гонки.
**Защита.** Начинать с гипотезы, выбирать подходящий профиль, сравнивать до/после.

## 12. Backpressure и bounded concurrency
**Устройство.** Ограничение одновременно работающих задач стабилизирует потребление памяти/подключений/CPU.
**Каверза.** `go handle(x)` на каждый входящий запрос без лимита может накопить огромное число горутин, даже если scheduler справляется.
**Защита.** Ограниченные worker pools/semaphore, bounded queues, отказ/замедление при перегрузе.

## 13. Shutdown сервера
**Устройство.** Остановка принятия новых запросов и ожидание уже выполняющихся — отдельные этапы.
**Каверза.** `Server.Shutdown(ctx)` не означает автоматического завершения всех произвольных фоновых горутин приложения.
**Защита.** Собственный жизненный цикл фоновых задач, cancel, WaitGroup/errgroup, остановка внешних ресурсов.

## 14. Cancellation vs delivery guarantee
**Устройство.** Channel и context координируют работу внутри процесса.
**Каверза.** «Всё отправлено в канал» ≠ «обработано и надёжно записано»: при падении процесса данные теряются.
**Защита.** При требованиях сохранности — БД, брокер, журнал, acknowledgements, idempotency.
