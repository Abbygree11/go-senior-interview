# Go runtime, горутины, память и GC

## 1. GMP: G, M, P
**Устройство.** G — исполняемая горутина и её состояние; M — поток ОС; P — ресурс планировщика, необходимый для исполнения Go-кода. `GOMAXPROCS` ограничивает число P, а не количество горутин.
**Каверза.** «100 000 горутин = 100 000 потоков» — неверно. Заблокированные горутины обычно не занимают отдельный поток ОС.
**Практика.** CPU-bound задачи ограничивать по реальной доступной параллельности; I/O-bound — по нагрузке, соединениям и ресурсам.

## 2. Блокирующие системные вызовы
**Устройство.** На блокирующем syscall поток M может задержаться; runtime умеет передавать P другому M, чтобы остальные G продолжали выполняться. При возвращении syscall горутина должна снова получить возможность исполняться на P.
**Каверза.** Не каждый I/O вызов обязательно блокирует M: сетевой I/O в типичных случаях интегрирован с netpoller.
**Практика.** Не путать syscall, ожидание канала и пользовательскую CPU-нагрузку; различать goroutine block profile и профили потоков.

## 3. Netpoller
**Устройство.** Runtime использует механизмы ОС для ожидания готовности сетевых дескрипторов, паркуя G вместо постоянного блокирования выделенного потока на каждом сокете.
**Каверза.** «Одна горутина на соединение слишком дорого, потому что это поток» — нет. Но десятки тысяч соединений всё равно потребляют память, fd и ресурсы приложения.
**Практика.** Устанавливать deadlines, лимиты соединений, backpressure.

## 4. Стек горутины
**Устройство.** Стеки горутин стартуют небольшими и могут расти/сжиматься под управлением runtime.
**Каверза.** Нельзя предполагать, что адрес локального объекта на стеке остаётся навсегда физически неизменным; корректность указателей поддерживает runtime.
**Практика.** Глубокая рекурсия и массивные локальные данные всё ещё могут быть дорогими.

## 5. Escape analysis
**Устройство.** Компилятор определяет, может ли объект безопасно жить в стеке или должен пережить текущий вызов; тогда его размещают в куче.
**Каверза.** `new(T)` не означает «обязательно в куче», а возврат указателя не во всех случаях гарантирует именно heap allocation — решает оптимизатор.
**Практика.** Проверять `go build -gcflags=-m=2`, `-benchmem`; не оптимизировать по догадкам.

## 6. GC: трёхцветная маркировка и write barriers
**Устройство.** Go использует конкурентную сборку мусора с маркировкой достижимых объектов и барьерами записи для сохранения корректности во время изменяющегося графа ссылок.
**Каверза.** Циклические ссылки сами по себе не предотвращают сборку: важна достижимость от корней. GC не гарантирует немедленного освобождения при исчезновении ссылки.
**Практика.** Понимать живой heap, скорость аллокаций, GC CPU и latency; смотреть `gctrace` и `pprof`.

## 7. `GOGC` и лимит памяти
**Устройство.** `GOGC` влияет на целевой рост живой кучи между циклами GC; `GOMEMLIMIT` задаёт мягкий ориентир памяти, учитываемой runtime.
**Каверза.** Это не жёсткий предел RSS и не способ гарантированно избежать OOM: при высокой нагрузке или внешних аллокациях память может превысить лимит.
**Практика.** Снимать метрики `runtime/metrics`, heap profiles; учитывать контейнерный memory limit.

## 8. `sync.Pool` и GC
**Устройство.** Пул предназначен для временного переиспользования объектов и снижения аллокаций.
**Каверза.** Элемент может исчезнуть из пула в любое время: `sync.Pool` — не кэш с гарантированным хранением. Не хранить там состояние, потеря которого критична.
**Практика.** Проверять реальные результаты бенчмарками; не использовать объект после `Put`, если им может завладеть другая горутина.

## 9. Finalizers и cleanup
**Устройство.** Финализация привязана к обнаружению недостижимости и управляется GC.
**Каверза.** На timely cleanup finalizer полагаться нельзя, а при завершении процесса он может не выполниться.
**Практика.** Явные `Close`/shutdown для файлов, сокетов, транзакций.

## 10. `GOMAXPROCS`, CPU и параллелизм
**Устройство.** `GOMAXPROCS` задаёт максимум P для одновременного исполнения Go-кода, не максимум активных goroutines и не число всех M.
**Каверза.** Увеличение `GOMAXPROCS` не ускоряет автоматически workload: конкуренция, memory bandwidth и блокировки могут доминировать.
**Практика.** CPU profile + нагрузочные тесты, измерять tail latency.

## 11. Preemption и tight loops
**Устройство.** Планировщик поддерживает вытеснение горутин; поведение зависит от версии runtime и safe points.
**Каверза.** «Горутина уступает управление только на `time.Sleep`» — устаревшее упрощение. При этом длинные CPU-bound участки могут влиять на задержки.
**Практика.** Не подменять синхронизацию надеждой на расписание; корректно проверять `ctx.Done()` при длительной работе.

## 12. Deadlock, starvation, livelock
**Устройство.** Deadlock — отсутствие прогресса из-за взаимного ожидания; starvation — некоторые участники не получают ресурс; livelock — активность без полезного прогресса.
**Каверза.** Runtime может выявить глобальный deadlock, но не обязан распознать каждый частичный deadlock или starvation.
**Практика.** Использовать goroutine dump, block/mutex profiles, таймауты и тесты с контекстом.
