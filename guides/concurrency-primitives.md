# Примитивы конкурентности: устройство → каверза → защита

## 1. `sync.Mutex`
**Устройство.** Взаимное исключение: один владелец критической секции в момент времени. Разблокирование устанавливает необходимую синхронизацию памяти для последующих захватов.
**Каверза.** Mutex не реентерабелен; повторный `Lock` без `Unlock` приводит к ожиданию самого себя. `Unlock` незаблокированного mutex — фатальная ошибка. Не копировать mutex после начала использования.
**Защита.** Сокращать критические секции; `defer Unlock` после успешного захвата, учитывать цикл жизни.

## 2. `sync.RWMutex`
**Устройство.** Несколько читателей одновременно или один писатель эксклюзивно. Ожидающий писатель препятствует новым `RLock`, чтобы не голодать.
**Каверза.** Нельзя безопасно повышать `RLock` до `Lock` и понижать обратно без отпускания; рекурсивный `RLock` может зависнуть при ожидающем писателе. При коротких секциях и конкурентной записи `RWMutex` иногда хуже `Mutex`.
**Защита.** Выбирать по профилю нагрузки и бенчмаркам.

## 3. `sync/atomic`
**Устройство.** `Load`, `Store`, `Add`, `Swap`, `CompareAndSwap` выполняют атомарные операции над отдельными поддерживаемыми значениями; Go atomics предоставляют последовательную согласованность (sequential consistency).
**Каверза.** Атомарность одного поля не гарантирует целостность инварианта из нескольких полей. `counter++` без atomic — гонка. CAS может проиграть и требует цикла повторных попыток. Нельзя смешивать обычные обращения с конкурентными atomic-записями.
**Защита.** Типизированные `atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`; для комплексного состояния — mutex/immutable snapshot.

## 4. `atomic.Value`
**Устройство.** Атомарная публикация/чтение интерфейсного значения, удобно для immutable конфигураций.
**Каверза.** Нельзя `Store(nil)`; все `Store` должны иметь один и тот же конкретный тип, иначе panic. После публикации **нельзя мутировать общий объект** без синхронизации.
**Защита.** Copy-on-write: собрать новый snapshot, один раз `Store`.

## 5. Unbuffered channel
**Устройство.** Отправка и приём должны встретиться; это передача значения с синхронизацией.
**Каверза.** Отправка без получателя блокирует; закрытие канала не «досылает» невыполненные отправки.
**Защита.** Продумать ответственность за `close`, ожидание читателя, отмену.

## 6. Buffered channel
**Устройство.** Буфер позволяет отправить без немедленного приёма, пока есть свободная ёмкость.
**Каверза.** Буфер не обеспечивает отсутствие deadlock и не является бесконечной очередью; `len(ch)` меняется конкурентно и не годится для решений «безопасно ли сейчас отправлять».
**Защита.** Backpressure, `select` с `ctx.Done()`, измеримые ограничения буфера.

## 7. `nil` и закрытый channel
**Устройство.** Отправка/приём `nil`-канала блокируются бесконечно; запись в закрытый канал — panic, чтение закрытого после исчерпания буфера — zero value + `ok=false`.
**Каверза.** В `select` `nil`-ветка отключена, а чтение из закрытого канала постоянно готово и может вызвать busy loop.
**Защита.** После `!ok` сделать `ch = nil` (если надо отключить ветку), либо выйти.

## 8. `select` и псевдослучайность
**Устройство.** При нескольких готовых операциях выбирается одна из них псевдослучайным образом; `default` выполняется, только если нет готовых операций.
**Каверза.** Нет гарантированного приоритета `ctx.Done()`: при отмене и одновременно готовой отправке отправка всё ещё может произойти.
**Защита.** Для строгого инварианта запрета поздних отправок нужен отдельный протокол синхронизации, не просто `select`.

## 9. Закрытие канала с несколькими отправителями
**Устройство.** `close(ch)` — сигнал «новых значений больше не будет», а не команда остановить отправителей.
**Каверза.** `cancel()` не означает, что все отправители остановились: `close` сразу после cancel может вызвать `send on closed channel`.
**Защита.** Производители учитывают отмену; координатор ждёт `WaitGroup`, затем единственный раз закрывает канал; потребитель продолжает чтение или организованно отменяется.

## 10. `sync.WaitGroup`
**Устройство.** Счётчик незавершённых работ; `Wait` ожидает обнуления; `Done` уменьшает счётчик, а `Add` увеличивает.
**Каверза.** Отрицательный счётчик вызывает panic. Если новый `Add` для пустой группы происходит одновременно с `Wait`, нарушается контракт; `WaitGroup` нельзя копировать после начала использования. `WaitGroup` не сообщает об ошибках и не отменяет задачи.
**Защита.** `Add` до старта горутин или `WaitGroup.Go` (в версиях Go, где доступен); `defer Done`; для ошибок/отмены полезна `errgroup`.

## 11. `sync.Once`
**Устройство.** Функция `Do(f)` выполняется ровно однажды для конкретного экземпляра `Once`; остальные вызовы ждут завершения.
**Каверза.** Если `f` запаникует, `Once` считает её выполненной: повторной попытки не будет. Рекурсивный `Do` того же `Once` блокируется.
**Защита.** Для инициализации с возвратом значения/ошибки использовать `sync.OnceValue`/`OnceValues` там, где подходит; спроектировать retry отдельно, если он нужен.

## 12. `sync.Cond`
**Устройство.** `Wait` атомарно отпускает связанный lock и ждёт уведомления, после пробуждения снова захватывает lock.
**Каверза.** `Signal` — не накопленный токен, а `Wait` не гарантирует, что условие всё ещё истинно. Без цикла проверки возможна неверная логика.
**Защита.** Канонический шаблон: `L.Lock(); for !condition() { c.Wait() }; ...; L.Unlock()`.

## 13. `sync.Map`
**Устройство.** Конкурентная map со специализированным API; оптимальна для некоторых read-mostly и disjoint-key нагрузок.
**Каверза.** `Range` не даёт атомарный snapshot, набор `Load` + `Store` не становится одной атомарной транзакцией; хранение `any` ослабляет проверку типов.
**Защита.** Использовать `LoadOrStore`/`CompareAndSwap` для поддерживаемой атомарной операции; для сложных инвариантов — обычная `map` + mutex.

## 14. Happens-before и data race
**Устройство.** Go memory model задаёт отношения порядка между операциями; mutex, channel, atomics дают гарантии видимости при корректном использовании.
**Каверза.** «На моей машине работает» не оправдывает чтение общей переменной без синхронизации. `time.Sleep` не создаёт happens-before.
**Защита.** `go test -race`, синхронизация; по возможности передача владения данными через канал.

## 15. Goroutine leaks при cancel
**Устройство.** `context.Context` предоставляет сигнал отмены, но не прерывает произвольный заблокированный оператор `ch <- x`.
**Каверза.** `cancel()` без учёта в `select` не спасает от блокировки на переполненном канале.
**Защита.**
```go
select {
case results <- v:
case <-ctx.Done():
    return
}
```
Если обе ветки готовы, отправка после отмены возможна.

## 16. `sync.Pool`
**Устройство.** Временное хранилище объектов для повторного использования, без гарантии удержания.
**Каверза.** GC может убрать элементы из пула; объект после `Put` больше нельзя продолжать менять как эксклюзивно свой.
**Защита.** Обнулять чувствительное состояние, избегать aliasing и измерять пользу.
